# 2026-08-15 工作日志

## 产品架构讨论：harness 现状与建议

- 结论：知己桌面端"有 harness，但是最小化的、单工作流专用"。LangGraph 三节点图 = 编排循环（harness 核心）；MemorySaver = 状态层；JSONL 审计 = 可观测性雏形；D级降级 = 局部回退。
- 缺失/薄弱的 harness 层：工具调度层（无函数调用/工具注册）、安全与权限闸（无沙箱/HITL）、长期记忆、通用错误重试、resume 能力（故 P3 暂停/恢复闸门未过）。
- 建议：当前不要为了"加 harness"而上通用 harness 框架（过度设计）；skill-runtime 本身已是 harness。若朝 agent 演进（P1-P4 闸门点亮），再按需补对应 harness 层——工具调度随 P3、resume 随 P2/P3、安全闸随工具可用。
- 关联：与前两轮"是否算 agent / 是否升级成 agent"结论一致——增量演进、闸门驱动，不整体重写。

## 架构对比：知己桌面端 vs 用户用 codex/workbuddy 开文件夹跑 skill

- 本质区别：**harness 是谁、谁在环**。知己桌面端 = 产品自身内嵌 runtime（LangGraph）作 harness，终端用户不在环、离线定时跑；用户工作流 = codex/workbuddy 通用 agent 作 harness，用户在环、交互式驱动 SKILL.md。
- 两者互补非竞争：知己桌面端是"交付给终端用户的产品"；codex/workbuddy 工作流是"开发者构建/维护知己的工具链"。同一套 skill 文件两边复用。
- 关键架构风险：skill 逻辑存在双份——SKILL.md（给 agent 看）+ TypeScript runtime 重新实现（给产品跑），有漂移/重复维护成本。后续应评估"runtime 直接消费 SKILL.md"还是"单一事实源"。
