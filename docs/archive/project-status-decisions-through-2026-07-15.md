# 项目状态历史决策归档

这些记录保留历史理由，不再作为每次会话的默认上下文。

| 日期 | 决策 | 理由 |
|------|------|------|
| 2026-07-13 | 周复盘恢复用户回应区而非新增多轮 workflow | 现有自动链路能生成周报事实和模式，但缺少用户补充遗漏与方向取舍的入口；固定报告末尾空模板比新增交互 workflow 更轻，也能让用户回应进入同一份周志文件 |
| 2026-07-12 | 主题思考改为 0-6 编号阅读路径 | 主题文件首先服务阅读和执行：行动卡前置且表格化，标题固定为 0. 当前行动卡 到 6. 我的观点演化路径，下一步优先步骤化，降低长主题文件的定位和执行成本 |
| 2026-07-12 | 主题行动层区分短期入口与长期动作 | 主题思考不是日反馈或周复盘，行动卡不再默认一周反馈；“值得保留的行动”统一写成长久可复用的行动表，降低抽象口号和过细技巧混杂的问题 |
| 2026-07-11 | 分析标准默认共享、视角定义暂不收敛 | 分析质量标准会影响所有复盘输出的维护契约，值得纳入 shared 自动检查；视角提示词差异当前不构成高风险维护点，继续作为用户版 override，避免为低收益一致性消耗维护成本 |
| 2026-07-11 | 将 90 天作为历史观点复查线而非过期线 | 具体观点需要优先参考最近证据和当前表达，但长期价值与已验证模式不应仅因时间超过 3 个月自动失效 |
| 2026-07-11 | 按风险批次收敛 shared 文件 | 已有质量基线和边界测试后，可把忽略行尾后等价的低风险文件批量收敛，减少一文件一提交的摩擦 |
| 2026-07-11 | 纯运行辅助文件优先收敛为 shared | `runtime-contracts.js` 和 workflow `shared.js` 不应按用户版变体双维护；统一为逐字节 shared 可降低摘要解析与运行镜像漂移风险 |
| 2026-07-11 | 质量基线先覆盖组件边界，再进入文本去重 | 防止优化阶段把“少文本”误当成“质量更高”；先证明入口、路径、摘要、降级、用户版边界不变 |
| 2026-07-11 | 用户版差异必须进入边界清单并接受测试 | 共享文件逐字节一致，用户版 override 必须有稳定理由，避免“看起来能用但不知道为什么不同”的维护债 |
| 2026-07-11 | 主题思考采用“单一运行契约 + 最小常驻入口 + 动态主题文件” | 详细逻辑集中维护，根入口只负责发现索引；用户确认后才能写入任意新主题，避免固定分类、日志自动摘录和全量上下文读取 |
| 2026-07-11 | 主题思考固定为可演化结构 | 用用户可读结构替代抽象档案字段；把事实/推断/建议区分、严肃反例审查和单一进行中实验收进现有契约，既保留思考痕迹又防止主题文件沦为无行动的信息堆积 |
| 2026-07-11 | 主题板块按实际需要分配篇幅 | 主题结构是闭环检查清单而非等长栏目；有行动、反例或高风险判断时应展开，无新证据时应短写并说明，防止形式整齐却无法指导行动 |
| 2026-07-11 | 新增能力必须先通过四项必要性闸门 | 最近一次推测性功能经历完整回退，说明仅有开发前提醒不足；今后缺少当前证据、核心目标、最简方案或即时验证路径时先停止并劝阻 |
| 2026-07-10 | 日志输入质量改按证据充分度而不是模板遵从度判断 | 保持自由叙事低摩擦，同时让分析深度与可用证据匹配，输入不足时降级而不是补全故事 |
| 2026-07-10 | 验证沉淀区分行为假说与单次干预实验 | 一次行动失败只能说明本次方法未奏效，不能直接证伪长期行为模式 |
| 2026-07-05 | 采用“命令 -> 代理 -> 视角”三层结构 | 分离入口、执行与分析定义，降低耦合 |
| 2026-07-05 | 视角拆分为生活内容视角与方法论视角 | 同时覆盖内容洞察与写作/复盘质量评估 |
| 2026-07-05 | 支持单文件整月日志 | 适配真实使用方式，而不是强制用户改习惯 |
| 2026-07-07 | `.claude/` 固化为唯一运行真相 | 避免 `.codex/` 与 `.claude/` 双份漂移 |
| 2026-07-07 | 日反馈统一走 `daily-analyzer` 契约 | 保证 `/daily-review` 与日志粘贴入口输出一致 |
| 2026-07-08 | 周/月/项目复盘统一为“复盘六问”外壳 | 降低不同复盘形态之间的认知切换成本 |
| 2026-07-08 | 引入 `/life-design` 作为低频方向校准入口 | 把人生设计从一次性灵感提示收敛为长期验证链路 |
| 2026-07-08 | 治理文档按“入口 / 状态 / 发布 / 规范”分工 | 减少重复叙述与维护漂移 |
| 2026-07-08 | 日反馈默认收紧为“单洞察 + 单动作”短反馈 | 降低阅读摩擦，优先保障次日验证闭环 |
| 2026-07-08 | 运行提示词按上下文预算拆分任务契约 | 让日反馈、复盘综合和证据验证只读取各自所需的最小充分规则 |
| 2026-07-08 | 复盘类命令默认走运行快路径 | 先消费已有反馈、验证沉淀与视角证据包，只有证据冲突或引用缺失时才扩大到原始日志 |
| 2026-07-09 | 为日/周/月/life-design 快路径补齐验收与执行保险丝 | 验收说明负责检查是否达标，执行前检查与防偏离规则负责降低“没走优化方案”的概率 |
| 2026-07-09 | `grill-me` 只作为开发态需求校准 skill 参与路由 | 区分开发辅助能力与用户运行时能力，避免需求拷问模式泄漏到终端用户体验 |
| 2026-07-09 | 中文治理文档统一以 UTF-8 作为开发与读取基线 | 根因是 Windows 终端输出链路可出现乱码假象，因此用 `.editorconfig` 与规范约束显式收口，避免把显示问题误判为文件损坏 |
| 2026-07-09 | 第一轮外部试用默认收缩到“今天日志”入口 | 优先验证日反馈的准确性、有用性与后续日志验证痕迹，避免多入口和完整仓库形态污染早期内测结果 |
| 2026-07-09 | 新增 `zhiji-user/` 作为用户版分发包 | 主仓库继续负责开发演进，用户版目录只承载内测使用所需文件，降低非开发用户的首次理解成本 |

| 2026-07-09 | 维护者自己的长期真实使用默认保留在主项目 | 主项目是最新运行真相；`zhiji-user/` 的主要职责是模拟终端用户体验与分发验收，混用会削弱开发态验证和用户态验收的边界 |
