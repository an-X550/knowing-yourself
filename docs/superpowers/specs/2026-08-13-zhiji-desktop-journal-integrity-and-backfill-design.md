# 知己 Windows 客户端日志完整性与历史补写设计

## 1. 结论

当前最需要解决的不是继续增加首页能力，而是恢复日志系统最基本的可信度：用户每次明确保存一条记录，都不能静默丢失已有内容；用户补写过去经历时，日期必须成为可选择的业务属性，而不能由软件强制等于今天。

本方案把已发现的日志覆盖问题、编辑后反馈过期问题，以及用户提出的“自选日期补写历史日志”合并为一个闭环：

```text
新建一条日志（默认今天，可选过去日期）
→ 独立保存，不覆盖同日其他日志
→ 必要时从历史显式编辑某一条
→ 今日反馈汇总当天全部日志
→ 周/月/项目复盘自然消费补写后的材料
```

首版继续使用 Electron、React、TypeScript、本地 Markdown、现有安全 IPC 和用户自己的 OpenAI 兼容接口；不引入数据库、云同步、账号、富文本编辑器或复杂版本系统。

## 2. 第一性原理审核

### 2.1 真实问题

日志系统的价值不是“有一个输入框”，而是长期保存可追溯的个人证据，供日反馈和周期复盘使用。由此得到四条不可突破的约束：

1. **保存不可导致静默丢失**：新建记录不能覆盖任何旧记录。
2. **身份与日期必须分离**：同一天可以有多条记录；日期不是日志主键。
3. **分析必须读取用户刚确认保存的内容**：界面草稿、磁盘正文和 AI 材料必须一致。
4. **历史补写必须真实进入后续分析**：补写日期用于材料归属，但不能伪造创建时间。

当前实现违反前三项：Renderer 自动选择当天第一条日志并携带其 ID；应用层因此执行更新；Repository 又固定写入 `journals/<year>/YYYY-MM-DD.md`。现有测试还把“替换每日文件”当成期望行为。修改已有日志后，生成日反馈可能读取磁盘旧正文；已有日反馈也会直接复用，不判断源日志是否更新。

### 2.2 新功能必要性闸门

“自选日期补写日志”值得现在实现：

- 有当前证据：用户已经尝试补写历史日志但找不到入口。
- 直接服务核心目标：更多真实历史材料能改善周/月/项目复盘的证据完整度。
- 无更简单替代：修改系统日期、手工改 Markdown 或使用 CLI 都不适合普通用户。
- 可立即验证：选择过去日期保存后，记录应出现在对应日期并进入指定范围的材料预览。

### 2.3 排除的惯性方案

以下方案不采用：

- **继续“一天一个文件”，把新正文追加到末尾**：实现快，但无法独立编辑、关联项目或追踪反馈来源，未来仍会拆分。
- **给今天页加日期选择，但保留按日期覆盖**：只扩大了覆盖范围，会让用户连历史日志也能覆盖。
- **立即引入 SQLite**：能解决唯一性和查询，但当前数据量、本地可读性和迁移成本不支持这一复杂度。
- **保存每次修改的完整版本历史**：尚无真实需求，不能替代正确的新建/编辑边界。

推荐方案是“多条 Markdown 记录 + 稳定 ID + 显式创建/编辑”。它解决根因，改动范围仍可控制在现有 Renderer、IPC、Application、Repository 和测试层。

## 3. 产品行为

### 3.1 新建日志

日志页默认进入“新建记录”，编辑器为空，日期默认本地当天。日期字段可选择今天或任意过去日期，首版不允许未来日期。

页面保持一个主操作：

- 未配置 AI：`保存这条记录`
- 已配置 AI 且日期为今天：`保存并更新今日反馈`
- 已配置 AI 且日期早于今天：`保存这条记录`

补写历史日志后不自动生成历史日反馈。原因是用户的直接目标是补充证据，自动调用 AI 会增加费用并制造大量旧反馈。保存成功后提供低权重动作 `查看这一天的记录`；周期复盘材料会立即包含该记录。

### 3.2 日期选择

日期选择位于项目选择之前，默认值为本地日期而非 UTC 日期。选择过去日期时显示一句短说明：

> 这条记录会归入所选日期，并参与覆盖该日期的周、月或项目复盘。

日期是经历归属日期；`createdAt` 仍记录实际创建时间，`updatedAt` 记录最后修改时间。这样既支持补写，也不伪装成当时创建。

### 3.3 同日多条记录

同一天可保存任意多条日志，每条拥有独立 ID、正文和项目关联。保存成功后，新建页清空正文并保留当前选择日期，方便连续补写；同时提供 `查看已保存记录`。

“本周 3 篇日志”仍按记录条数计算，但首页推荐理由改为“本周已有 N 条记录”，避免把同一天三条误称为三天。是否未来改为“至少 3 个有记录日期”留待真实使用数据，不在本轮扩大规则。

### 3.4 显式编辑

新建页不自动载入当天已有日志。用户只能在“过去日志”中选择某条记录并点击 `编辑`，随后进入编辑状态：

- 页面标题显示 `编辑记录 · YYYY-MM-DD`。
- 保存只更新该 ID 对应的文件。
- 提供 `取消编辑`，返回历史且不保存草稿。
- 日期可以修改为今天或过去日期；修改日期时移动该记录，而不是复制出第二个同 ID 文件。

首版不提供删除，以避免在尚无回收站时引入不可恢复操作。

### 3.5 未保存草稿

正文或日期发生变化后，如果用户切换一级导航或进入历史，显示应用内确认：`这条记录还没有保存。放弃更改吗？`。不使用浏览器原生弹窗，不做自动保存。关闭程序时沿用同一判断；如果 Electron 当前没有关闭拦截契约，本轮至少先覆盖应用内导航，窗口关闭保护作为同一发布的验收项。

## 4. 数据模型与本地文件

### 4.1 文件命名

新日志使用稳定且不冲突的路径：

```text
<数据目录>/journals/<year>/<date>--<journal-id>.md
```

示例：

```text
journals/2026/2026-08-13--journal_8f31c2.md
```

文件内容继续使用现有 Schema：

```yaml
schema_version: 1
id: journal_8f31c2
date: '2026-08-13'
created_at: '2026-08-20T09:10:00+08:00'
updated_at: '2026-08-20T09:10:00+08:00'
project_ids: []
```

不需要升级 Journal Schema 版本；变化发生在集合约束和文件寻址规则，而不是单条记录字段。

### 4.2 创建与更新契约

不再使用一个带可选 `id` 的模糊 `save` 契约。改为：

```ts
type CreateJournalInput = {
  date: string;
  body: string;
  projectIds: string[];
};

type UpdateJournalInput = {
  id: string;
  date: string;
  body: string;
  projectIds: string[];
  expectedUpdatedAt: string;
};
```

- `create` 总是生成新 ID 和新文件，若目标意外存在则失败，绝不覆盖。
- `update` 必须先按 ID 找到原文件，并校验 `expectedUpdatedAt`，防止两个窗口或过期页面静默互相覆盖。
- 更新日期时先原子写入新路径并校验，再移除旧路径；任何一步失败都保留至少一个完整副本。
- Repository 读取时拒绝重复 ID，并返回明确的数据冲突错误。

Preload 只暴露具名的 `journals.create`、`journals.update`、`journals.list`、`journals.get`，Renderer 仍不能访问文件系统。

### 4.3 兼容已有文件

已有 `journals/<year>/YYYY-MM-DD.md` 必须继续可读、可编辑、可备份和可恢复。本轮不批量重命名、不自动删除旧文件：

- `list/get` 同时识别旧文件名和新文件名。
- 编辑旧日志时，优先更新原路径；如果用户修改日期，再安全迁移到新命名路径。
- 新建日志一律采用新路径。
- 备份业务校验新增“日志 ID 全局唯一”和“文件年份与业务日期一致”检查。

这样不会为了修复未来保存而冒险重写用户已有资料。

## 5. 日反馈与周期复盘一致性

### 5.1 今日反馈聚合

日反馈从“绑定一条日志”调整为“绑定当天全部日志”。生成前按日期获取当天记录，按 `createdAt` 排序，输入 AI 时保留每条记录的 ID、正文和项目关联。生成结果的 `sourceIds` 写入当天全部日志 ID。

开始页的判断改为：

```text
今天没有任何日志 → 写一条日志
今天有日志，且不存在覆盖全部当前日志版本的日反馈 → 生成/更新今日反馈
其他规则保持不变
```

为了判断反馈是否过期，Review 增加来源版本快照，而不是只比较 ID：

```ts
sourceVersions: Array<{ id: string; updatedAt: string }>;
```

这是 Review Schema v2。旧 Review v1 继续读取，但只要当天日志发生过修改或新增，旧反馈视为需要更新。重新生成时保存一份新的反馈文件，不覆盖旧反馈；历史中标记最新一份，旧结果仍可追溯。

### 5.2 保存再生成

`保存并更新今日反馈` 必须严格串行：

```text
create/update 成功并返回已落盘 Journal
→ refresh 当天日志集合
→ 用最新集合生成反馈
→ refresh 全局 journals/reviews
→ 原位展示新反馈
```

保存失败时绝不调用 AI；AI 失败时已保存日志仍保留，并提供 `重试生成`。

### 5.3 历史补写的分析范围

- 周/月复盘：按日志业务日期选择材料，因此补写后自然进入对应周期。
- 项目复盘：选择了项目时，材料必须同时满足“关联该项目”以及用户选择的日期范围；当前实现的 `日期范围内 OR 关联项目` 会把范围内所有无关日志和范围外所有项目日志混入，需改为明确的交集语义。
- 仅按日期范围、不选项目时，项目复盘退化为自定义日期复盘，界面应明确称为“自定义范围复盘”。
- 已生成的旧周/月/项目复盘不自动失效或后台重算；再次预览相同范围时提示“材料自上次复盘后有新增或修改”，由用户决定是否重做。

## 6. 前端信息架构

一级导航不增加，仍为开始、日志、复盘、项目、设置。

日志页内部收敛为：

```text
日志
├─ 新建记录
│  ├─ 日期（默认今天，可选过去）
│  ├─ 项目（可选）
│  ├─ 正文
│  └─ 一个主操作
└─ 过去日志
   ├─ 日期 / 项目 / 正文搜索
   ├─ 同日多条记录列表
   └─ 阅读 / 显式编辑
```

同日多条记录在列表中除日期外显示创建时间和正文首行，避免出现多个视觉上完全相同的条目。历史列表按 `date DESC, createdAt DESC` 排序。

开始页只统计和推荐，不承载日期控件。用户点击“开始记录”后在日志页决定是否补写历史，避免首页再次复杂化。

## 7. 错误与安全边界

- 新建路径冲突：生成新 ID 后重试一次；仍冲突则报错，不覆盖。
- 更新目标不存在：提示“记录已移动或不存在”，保留编辑器草稿。
- `expectedUpdatedAt` 不一致：提示“这条记录已在其他位置更新”，提供重新载入；不自动合并正文。
- 日期非法或未来日期：IPC Schema 拒绝，前端同时限制选择。
- 修改日期迁移失败：旧文件保持不变，界面显示失败。
- 重复 ID、同一文件的 frontmatter 日期与目录年份冲突：启动读取失败页给出具体文件路径，不静默忽略。
- 导出继续包含全部日志；恢复仍只进入空目录，并在切换前验证多日志与 Review v1/v2 关系。
- 不增加删除、覆盖确认、批量改日期或自动合并，避免引入新的不可恢复路径。

## 8. 测试与验收

### 8.1 Repository 与应用层

必须覆盖：

1. 同一日期创建两条日志，得到两个 ID、两个文件，正文均可读取。
2. 更新其中一条只改变目标文件。
3. 修改日期后旧路径消失、新路径存在，ID 与 `createdAt` 不变。
4. 旧 `YYYY-MM-DD.md` 与新文件可同时读取。
5. 重复 ID、过期 `expectedUpdatedAt` 和未来日期被拒绝且不改变磁盘。
6. 备份与恢复能往返同日多条日志，并拒绝重复 ID。

### 8.2 Renderer

必须覆盖：

1. 新建页默认空白且日期为本地今天，不加载当天旧正文。
2. 用户可选择过去日期，不能选择未来日期。
3. 连续保存两条不会在第二次请求中携带第一条 ID。
4. 只有从历史点击编辑才调用 `update`。
5. 有未保存草稿时切换页面需要确认。
6. 编辑后点击生成会先完成保存，再把最新已落盘材料交给反馈生成。

### 8.3 E2E

使用隔离数据目录验证完整真实链路：

```text
今天保存第一条
→ 今天保存第二条
→ 选择昨天补写第三条
→ 重启应用
→ 历史中三条均存在且正文独立
→ 编辑今天第一条，不影响第二条
→ 生成今日反馈，sourceIds 覆盖今天两条最新记录
→ 预览包含昨天的周期材料，能看到补写日志
→ 导出备份并验证包含三个日志文件
```

现有单条 E2E 不能继续作为日志完整性的充分证据。

## 9. 实施优先级

### P0：恢复数据可信度

1. 拆分 create/update IPC 与应用用例。
2. 新文件名改为日期加稳定 ID，兼容读取旧文件。
3. 日志页默认新建空白；历史显式进入编辑。
4. 修复保存后再生成、日反馈过期判断。
5. 增加同日两条、编辑隔离、重启保留的自动化测试。

### P1：历史补写闭环

1. 增加今天或过去日期选择和说明。
2. 补写记录进入周/月/项目材料预览。
3. 修正项目材料的项目与日期交集语义。
4. 增加未保存草稿保护和同日多条历史展示。
5. 扩展备份恢复业务校验。

P0 与 P1 应作为同一次开发计划连续交付：日期选择依赖正确的多记录模型，不能先把日期控件接到旧覆盖仓储上。

### 暂缓

- 删除与回收站
- 日志版本时间线
- 富文本、图片和附件
- 标签系统和全文索引数据库
- 自动补写或 AI 猜测日志日期
- 自动重算全部历史反馈与复盘
- 云同步、多设备冲突合并和协作账号

这些能力没有当前证据，且会显著扩大数据安全与交互复杂度。

## 10. 完成定义

只有以下事实同时成立，本方案才算落地：

- 同一天连续保存多条日志不会覆盖。
- 用户能选择今天或过去日期新建记录。
- 新建与编辑在界面、IPC 和文件写入层均明确分离。
- 生成反馈读取的是最后确认保存的全部今日日志。
- 补写日志能在对应周/月/项目材料预览中出现。
- 旧日期文件无需迁移即可继续读取、编辑、导出和恢复。
- 自动化覆盖同日多条、显式编辑、历史补写、重启、分析和备份闭环。
- 未进行真实 3–5 人测试前，不声称日期补写入口已被普通用户验证为易懂。
