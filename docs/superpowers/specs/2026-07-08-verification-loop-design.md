# 日反馈验证闭环设计

## 背景

项目已经能产生日反馈、周报和月报，但 `关于我/verified-patterns.md` 仍为空，说明“洞察 -> 行动 -> 验证 -> 沉淀”没有成为默认路径。继续增强报告会提高叙述质量，却不能保证用户发生行为改变。

## 目标

让现有最短入口 `/daily-review` 与 `log` skill 在生成日反馈后，自动完成上一条行动的验证判断，并把结果沉淀到 `关于我/verified-patterns.md`。

## 非目标

- 不新增命令。
- 不新增视角。
- 不改周/月报一级标题协议。
- 不追求自动化脚本解析；本轮只强化 agent/command 运行契约。

## 设计

### 1. 日反馈成为验证入口

`daily-analyzer` 在读取上一条日反馈时，不只提取 `⚡ 明天试试`，也提取 `💊` 行中的新认知、行动和验证状态。今天的日志必须判断上一条行动是否成立：

- `✅ 做到了`
- `❌ 没做`
- `⚠️ 证据不足`

判断必须引用今天日志证据。无上一条日反馈时跳过。

### 2. 调用方负责写回模式库

`daily-analyzer` 仍只返回文本，不写文件。`/daily-review` 和 `log` skill 在保存日反馈后，读取 `context.verified_patterns`，把上一条行动验证写入模式库：

- 第一次可判断：进入“待验证的假说”，状态写明本次结果。
- 同一假说累计 2 次成立：移入“已确认的模式”。
- 明确被推翻：移入或更新“已证伪的假说”。
- 证据不足：保留待验证，不升级。

### 3. 周/月报优先复盘验证状态

周报和月报继续使用六问结构，但在“评估结果”和“后续规划”中优先回答：

- 哪些日反馈行动被验证？
- 哪些行动连续没做？
- 哪些假说应进入 `verified-patterns.md`？
- 哪些建议应该降低门槛或停止重复？

### 4. 成功指标

第一阶段验收只看四项：

- 最近 7 天至少 5 次日反馈。
- 每次日反馈有上一条时都检查行动。
- `关于我/verified-patterns.md` 不再为空。
- 至少 1 条假说进入待验证、已确认或已证伪。

## 边界

如果日志没有足够证据，必须写“证据不足”，不能为了闭环硬判。验证闭环服务于行为学习，不服务于制造好看的成功记录。
