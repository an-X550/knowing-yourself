# 桌面端 P1：受确认的验证模式沉淀 — 架构规格

> **状态：必要性闸门未通过（2026-08-14）。** 本文是待触发规格，不是执行计划。只有在真实使用中出现跨日复用已验证模式的需求证据后，才可进入实施。

## 必要性闸门评估

| 闸门条件 | 当前状态 | 结论 |
|---|---|---|
| 1. 有当前、具体的问题证据 | JSONL 审计可追溯行动验证状态，但用户尚未在真实使用中表达"需要跨日复用已验证模式"的需求。PROJECT_STATUS 高优先级待办仍为"连续运行至少 5 次真实 /daily-review，验证 verified-patterns.md 写回质量"——真实跨日复用尚未发生。 | **不成立** |
| 2. 直接服务核心目标 | 知己核心目标是"从记录中发现模式，形成小行动，并在后续验证"。验证模式沉淀是核心闭环的一部分，但当前日反馈尚未产生足够的真实验证样本。 | 成立但缺乏前置证据 |
| 3. 既有能力不能更简单解决 | JSONL 审计已记录等级、结果和昨日行动状态。在用户尚未需要主动管理已验证模式前，审计文件的只读查询是更简单的替代方案。 | **不成立** |
| 4. 实现后能立即验证 | 需要先有真实验证样本才能验证。当前没有。 | **不成立** |

**结论：闸门未通过。** 不创建数据模型、页面、SQLite 或"记忆"。等待真实证据。

## 真实问题定义

### 什么情况下才需要 P1

用户在**真实使用中**出现以下场景之一：

1. 在后续日反馈或周期复盘中，用户主动要求"参考上次验证有效的某个模式"。
2. 用户发现 JSONL 审计难以查看、理解或管理——例如想看"过去 30 天哪些行动被标记为 done，它们有什么共性"。
3. 用户想确认或拒绝一个"候选验证模式"，而不是让它自动沉淀。

只有上述场景**实际发生**，才说明 JSONL 审计不足以满足用户需求。

### 什么情况下不需要 P1

- 用户只是偶尔查看审计记录 → JSONL 只读查询足够。
- 用户还没有连续使用日反馈足够多次 → 没有模式可沉淀。
- 用户想自动从旧日志归纳人格/模式 → 明确禁止，这违反"模型只能提出候选，用户明确确认后才保存"。

## 架构设计（获准后）

### 数据模型

```text
<dataRoot>/verified-patterns/verified-patterns.json
```

```ts
interface VerifiedPattern {
  id: string;                    // pattern_<uuid>
  createdAt: string;             // ISO 8601
  sourceReviewId: string;        // 来源日反馈 ID
  sourceDate: string;            // 来源日期
  evidenceSummary: string;       // 证据摘要（非全文）
  pattern: string;               // 用户确认的模式描述
  status: 'confirmed' | 'rejected' | 'superseded';
  confirmedAt?: string;          // 用户确认时间
}
```

- 只追加，不自动覆盖。`status` 变更需要用户明确确认。
- 不保存日志正文、API Key、模型原始回复或完整个人资料。
- 文件损坏时不能影响业务数据（journals/reviews）。

### 工作流

```text
日反馈生成 → 模型从 evidence 中提出候选模式（可选）
  → UI 展示候选：来源 review ID、证据摘要、模式描述
  → 用户确认或拒绝
  → 确认：原子写入 verified-patterns.json + 审计事件
  → 拒绝：记录 status=rejected（不删除）
  → 后续日反馈可只读引用已确认模式（不自动注入）
```

### 权限边界

| 动作 | 策略 |
|---|---|
| 读取 verified-patterns.json | 自动，只读 |
| 模型提出候选模式 | 自动，但候选不写入 |
| 确认/拒绝候选 | 用户明确操作 |
| 修改已确认模式 | 用户明确确认差异后 |
| 自动提取/归纳 | 禁止 |
| 向量检索/跨设备同步 | 不在范围内 |

### 与日反馈 Runtime 的关系

- 日反馈 Runtime **可选**读取已确认模式作为上下文补充（`materialCategories` 新增 `verified-patterns`）。
- 读取是只读的，不修改模式。
- 兼容快照版本升级为 `desktop-daily-feedback-v2`（如果材料范围变化）。

## 金样本要求

实施前必须准备：

1. 至少 5 次真实日反馈，其中至少 2 次行动被标记为 `done`。
2. 用户在后续日反馈中主动引用至少 1 个已验证模式的真实场景记录。
3. 脱敏的 verified-patterns.json 示例（含 confirmed、rejected、superseded 各一条）。

没有金样本不接入实现。

## 获准后的最小实施范围

1. `VerifiedPatternRepository`（JSON 仓储，原子写入 + 复读验证）
2. `VerifiedPatternCandidate` 类型（模型输出 Schema 的一部分）
3. UI：候选预览卡片（来源、证据摘要、确认/拒绝按钮）
4. UI：已确认模式只读列表
5. 日反馈 Runtime 可选读取已确认模式（不自动注入）
6. 审计事件扩展：`pattern_proposed`、`pattern_confirmed`、`pattern_rejected`
7. 隔离回归测试：verified-patterns 仓储不依赖 `.claude`

**不含**：自动提取、自动写入、向量检索、跨设备同步、通用长期记忆、SQLite。

## 触发条件

以下任一条件**实际发生**时，重新评估闸门：

1. 用户在真实日反馈使用中主动要求"参考上次验证有效的模式"。
2. JSONL 审计文件超过 100 条记录，用户表达查看/管理困难。
3. 用户连续 5 次日反馈中至少 2 次行动被标记为 `done`。

## 停止理由

- 当前日反馈垂直切片刚完成 P0 发布门，真实使用样本不足。
- JSONL 审计已能追溯验证状态，在用户未表达管理需求前不引入新数据模型。
- 提前实现会引入未被验证的复杂度（新仓储、新 UI、新 Schema），违反"不为未来假设重复造轮子"。

## 非目标

- 不把审计日志升格为长期记忆。
- 不自动从旧日志归纳人格或模式。
- 不引入 SQLite、向量库或跨设备同步。
- 不让模型自行决定写入、修改或删除验证模式。
