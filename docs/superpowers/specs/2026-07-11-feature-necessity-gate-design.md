# 新功能必要性闸门设计

## 背景

项目已有开发前闸门、Spec-Before-Code 和 `grill-me` 需求校准，但现有规则主要负责提醒、澄清和规划，没有明确规定“新功能缺少必要性时必须停止实施”。用户版自动健康采集经历了先实现、后发现目标不成立、再完整回退的过程，说明项目需要把“先判断是否值得做”固化为开发治理规则。

## 第一性原理判断

这条规则本身满足新增能力的四项标准：

1. 有当前问题证据：已发生一次推测性功能实施与回退。
2. 服务核心目标：减少无真实价值的功能和维护负担。
3. 现有提醒不足：缺少“不通过就停止”的明确执行语义。
4. 可以立即验证：下一次新增能力请求必须先输出必要性判断。

## 设计选择

只修改 `AGENTS.md` 和 `CLAUDE.md` 中的开发工作流规范，并保持两份文件逐字同步。

不新增 hook、agent、skill 或运行时 contract。原因是该规则只约束项目开发行为，治理文档本身就是权威入口；增加自动路由或新运行层会扩大误判、维护和同步成本。

`docs/first-principles.md` 已包含长期减法原则，本次不重复修改。`.claude/shared/ai-operating-principles.md` 面向日志分析运行行为，也不承担开发治理规则。

## 适用范围

闸门只适用于新增能力：

- command
- agent
- workflow
- skill
- hook
- 配置行为
- 报告形态
- 用户入口

以下维护工作不受该闸门阻挡：

- bug 修复
- 安全修复
- 兼容性修复
- 测试补齐
- 文档纠错
- 删除冗余

如果任务同时包含维护和新增能力，只对新增部分执行闸门；维护部分不得被捆绑需求阻塞。

## 必要性标准

新增能力必须同时满足：

1. 有当前、具体的问题证据，不是“未来可能需要”。
2. 直接服务项目核心目标或明确的面试叙事目标。
3. 现有能力、流程调整或删除复杂度无法更简单地解决。
4. 实现后能立即验证是否解决了问题。

## 执行流程

闸门发生在 spec、plan 和代码之前：

1. 识别请求是否包含新增能力。
2. 用四项标准给出简短必要性结论。
3. 四项全部满足时，继续现有 `brainstorming -> writing-plans -> executing-plans` 流程。
4. 任一项不满足时，停止实施，并说明：
   - 哪项证据缺失；
   - 继续开发的机会成本；
   - 可复用的现有能力或更简单替代方案；
   - 为什么建议现在不要做。
5. 用户阅读理由后，明确复述风险并再次要求继续，才允许覆盖本次劝阻并进入现有开发流程。

用户首次请求中的“直接改”“不用规划”“立即实现”不能跳过必要性判断；它们只能影响必要性通过后的流程深度。

## 输出边界

- 必要性判断默认简短，不生成新报告或评分表。
- 不把 AI 的判断变成永久否决；用户拥有知情覆盖权。
- 劝阻必须基于四项标准和项目证据，不使用空泛的“可能没必要”。
- 对通过闸门的需求不重复盘问已经明确的证据。

## 文件与发布影响

- 修改 `AGENTS.md`。
- 将同样内容逐字同步到 `CLAUDE.md`。
- 更新 `VERSION`、`PROJECT_STATUS.md` 和 `CHANGELOG.md`。
- README 只同步版本徽章；不新增功能说明，也不修改运行时 `.claude/`、用户版 overlay 或 `zhiji-user/`。

## 验证标准

1. `AGENTS.md` 与 `CLAUDE.md` SHA-256 一致。
2. 规范明确包含四项必要性标准、首次停止、知情二次坚持和维护例外。
3. 新规则位于工作流控制中，且先于 Spec-Before-Code。
4. VERSION、PROJECT_STATUS 和 README 徽章版本一致。
5. 现有回归测试继续通过。
