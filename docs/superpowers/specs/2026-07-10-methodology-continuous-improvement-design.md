# 方法论持续优化机制设计

## 目标

在保持“复盘六问”用户可见一级标题稳定的前提下，为视角文件、方法论规则和综合契约建立可持续优化机制。系统应在维护者开发热情下降后，仍能依靠真实使用与内测反馈主动发现问题、定期审计、验证候选改动，并按风险等级执行或请求确认。

成功标准：

1. 日反馈、周报、月报和内测反馈可以沉淀为不含用户原文的结构化方法论信号。
2. 方法论审计同时支持时间触发和异常阈值触发，不依赖维护者主动发起优化。
3. GPT 自检不能单独触发自动修改；用户反馈和后续行为证据优先。
4. L1 低风险和满足严格条件的 L2 中风险改动可以自动验证、更新版本并本地提交；L3 高风险改动必须等待人工批准。
5. 每项候选改动都有问题证据、修改假说、基线、回放结果、观察期和可追溯提交。
6. 自动审计和信号采集失败时，不阻断正常日志分析与复盘。
7. 用户版只采集和导出脱敏汇总，公共方法论只在主项目中演进。

## 第一性原理

方法论优化不是“让 GPT 多想一遍”，而是建立可观测、可归因、可验证、可恢复的反馈闭环：

```text
方法论版本
→ 产生分析结果
→ 用户反馈与后续行为
→ 定位方法单元
→ 提出单变量修改假说
→ 历史回放
→ 风险裁决
→ 真实使用观察
```

本设计继续遵守项目价值公式：

```text
价值 = (洞察质量 × 可行动性 × 闭环速度) / 使用摩擦
```

因此，方法论优化必须改善洞察、证据或行动效果，不能只增加规则数量、报告长度或架构完整性。

## 核心不变量

以下边界不能被自动审计突破：

- 复盘六问继续作为周报、月报和项目复盘的用户可见一级标题。
- 六问内部允许增加、删除、重组和收紧内容协议。
- 用户原文、身份和可反推个人的信息不进入方法论信号账本。
- 单次负面反馈不能触发普通方法论修改；隐私、安全和严重越界事件除外。
- 公共方法论不能根据单个用户直接定制；单用户证据只能标记为“尚未证明可迁移”。
- GPT 自检只能触发检查，不能单独触发自动修改。
- 风险分级规则不能由审计器自行放宽。
- 每次自动修改必须可定位、可回放、可观察、可恢复。
- 自动优化不能增加正常用户的必做步骤。

## 总体架构

采用“信号账本 + 审计引擎 + 风险闸门”架构：

```text
日反馈 / 周月复盘 / 内测反馈
              ↓
      质量信号采集器
              ↓
   脱敏方法论信号账本
              ↓
时间到期检查 + 异常阈值检查
              ↓
        方法论审计器
              ↓
      生成问题与修改假说
              ↓
       风险分级闸门
        ↙           ↘
低风险自动优化      高风险优化提案
        ↓           ↓
历史样本回放       等待用户批准
        ↘           ↙
       正常版本流程
```

各单元职责：

1. **质量信号采集器**：只采集反馈、行为结果和确定性自检信号，不直接决定如何改方法论。
2. **方法论信号账本**：保存脱敏结构化信号，作为审计证据来源，不进入 Git。
3. **双触发控制器**：在相关任务结束后检查时间和异常阈值，未触发时静默结束。
4. **方法论审计器**：区分执行偏差、样本问题和方法论缺陷，生成单变量修改假说。
5. **风险分级闸门**：依据固定规则决定自动执行或等待批准。
6. **回放验证器**：使用公开脱敏样本和本地真实样本比较新旧版本。
7. **方法论更新器**：通过验证后修改运行真相，执行版本、CHANGELOG 和本地提交流程。

## 信号模型

### 信号可信度

| 等级 | 来源 | 用途 |
|---|---|---|
| A | 用户明确认可、反驳、遗漏、重复、越界等反馈；内测脱敏汇总 | 可作为方法论改动的主要证据 |
| B | 行动是否执行、干预是否有效、洞察后续得到支持或出现反例 | 说明实际价值，需与方法单元归因结合 |
| C | GPT 检测到的视角重复、证据缺失、规则冲突、职责越界 | 只能触发检查，不能单独触发自动修改 |

### 信号类型

统一使用以下信号类型：

```text
useful / rejected / missing / repetitive / unsupported /
overreach / action_effective / action_failed
```

信号记录格式：

```yaml
date: 2026-08-12
source_type: maintainer | beta_aggregate | system_check
feature: daily-review | weekly-review | monthly-review | life-design
method_unit: perspective:coach | contract:review-synthesis | review-question:5
signal: repetitive
confidence: A | B | C
count: 1
period: 2026-08
summary: 不含用户原文的脱敏问题描述
status: open | auditing | observing | resolved | dismissed
```

内测数据必须在导入前聚合，只保留问题类型、数量和脱敏摘要，不保留身份、原文和单人明细。

## 双触发审计

系统不依赖后台常驻服务。每次相关分析任务完成后进行惰性到期检查；正常报告先交付，审计不得阻断报告生成。

### 每月轻审计

触发条件：

- 距上次轻审计满 30 天。
- 至少有 5 次有效运行，或 3 条 A/B 级信号。

检查范围：

- 重复、空泛、遗漏和无证据判断。
- 视角职责冲突。
- 自动修改的观察结果。
- 可安全自动修复的低风险问题。

样本不足时只生成审计延期记录，不做修改。

### 每季度深审计

触发条件：

- 距上次深审计满 90 天。
- 至少有 15 次有效运行。

检查范围：

- 每个视角的独特信息贡献。
- 六问内部内容协议。
- 评分量表是否产生模板偏见。
- 方法论是否过度适配维护者。
- 规则的保留、合并、降级或删除候选。

缺少内测汇总时仍可审计，但必须标记样本偏差和可迁移性不足。

### 异常触发

满足任一条件即可在时间审计前发起专项审计：

- 同一方法单元在至少 2 个日期出现 3 条 A/B 级负面信号。
- 同类问题同时出现在维护者和内测汇总中。
- 无证据心理归因、隐私问题或严重越界出现 1 次。
- 两个视角在 30 天内出现至少 5 次实质重复。
- 同一方法论建议连续 3 次没有执行，或执行后连续无效。
- 自动修改后出现 2 条新的 A 级反驳信号。
- 回归测试发现六问标题、证据边界或视角职责被破坏。

### 防抖与观察期

- 同一 `method_unit + signal` 审计后进入 30 天观察期。
- 观察期内普通重复信号只累计，不重复修改。
- 隐私、安全和严重越界信号可以绕过观察期。
- 自动修改后至少经过 3 次真实运行，才能判断保留或建议回退。

## 方法论质量指标

| 指标 | 定义 |
|---|---|
| 新洞察率 | 用户认为自己原本没有看到的发现比例 |
| 证据支持率 | 重要结论有可靠日期、原文或既有验证的比例 |
| 用户反驳率 | 被用户明确判断错误或偏离的结论比例 |
| 内容重复率 | 视角之间、六问章节之间实质重复的比例 |
| 行动转化率 | 建议转化成实际行为的比例 |
| 后续验证率 | 洞察或行动后来获得支持、反例或有效性结果的比例 |

没有反馈时对应指标必须标记为“未知”，不得由 GPT 猜测为正面结果。

## 风险分级

风险等级由稳定契约和机器可读策略共同定义。审计器不能修改本次候选改动的风险判定规则。

### L1：低风险，自动执行

必须同时满足：

- 不改变六问标题和用户可见结构。
- 不改变评分标准、视角数量或职责边界。
- 不增加心理、健康或人格归因。
- 不改变命令、参数、输入输出路径和 workflow 编排。
- 修改范围单一，并与现有上位契约一致。
- 至少有 3 条相关信号，其中至少 1 条为 A/B 级。
- 契约测试和历史样本回放全部通过。

允许的典型修改：删除重复提示、澄清证据要求、统一术语、补齐反例或证据不足约束、修复视角文件与共享契约的轻微漂移。

### L2：中风险，条件式自动执行

适用范围：收紧视角分析范围、调整六问内部内容要求、删除长期低价值检查项、调整主题归并规则、改变某类建议的生成条件或内部处理顺序。

必须同时满足：

- 至少 5 条 A/B 级信号。
- 覆盖至少 3 个日期或周期。
- 已检查反例。
- 至少通过 5 份历史样本回放。
- 一次只修改一个方法论变量。
- 核心指标改善，且未破坏原有有效洞察和稳定结构。
- 修改后进入 30 天或至少 3 次真实运行的观察期。

只有单用户证据时，必须标记“单用户验证，尚未证明可迁移”。

### L3：高风险，必须人工批准

包括：

- 修改或取消复盘六问。
- 新增、删除或合并视角。
- 修改六步法、复盘六问或六维图的评分标准。
- 改变心理归因、安全边界和人生建议边界。
- 修改风险分级、审计触发阈值或自动执行权限。
- 将个人经验写入公共方法论。
- 改变用户可见输出结构。
- 使用或保存更详细的内测用户数据。
- 同时修改多个相互依赖的方法论单元。

风险无法确定时一律按 L3 处理。

## 修改、回放与观察流程

每个候选修改按以下顺序处理：

```text
1. 明确问题
2. 定位方法单元
3. 写出修改假说
4. 保存基线结果
5. 只修改一个变量
6. 运行确定性契约测试
7. 运行历史样本回放
8. 比较新旧输出
9. 风险闸门裁决
10. 自动修改或生成提案
11. 进入真实使用观察期
```

回放分两层：

- **公开脱敏样本**：进入 `tests/` 或 `examples/`，用于稳定契约测试。
- **本地真实样本**：保留在 gitignored 数据目录，只在本机回放。

内测用户原文不能进入回放库；只有经过人工脱敏且无法反推身份的抽象样本才能成为公开 fixture。

确定性检查至少覆盖：

- 六问标题完整。
- 输出结构、路径和命令契约未被破坏。
- 未出现禁用词和越界表达。
- 重要结论有证据或明确标注“证据不足”。
- 视角没有输出职责禁止的内容。
- 风险政策与运行镜像保持同步。

内容质量比较至少覆盖：重复、有效洞察保留、无证据结论、行动具体性、新遗漏和模板化倾向。GPT 的内容评分只能作为辅助证据，用户反馈和后续行为结果优先。

## 文件职责

### 受版本控制的运行真相

| 文件 | 职责 |
|---|---|
| `.claude/shared/contracts/methodology-improvement.md` | 信号、触发、风险、观察期的权威运行契约 |
| `.claude/shared/methodology-risk-policy.json` | 供 workflow 和测试读取的机器可读风险规则 |
| `.claude/agents/methodology-auditor.md` | 问题归因、修改假说和证据充分度判断 |
| `.claude/commands/methodology-audit.md` | 手动审计、调试和自动触发复用入口 |
| `.claude/workflows/methodology-audit.js` | 到期检查、阈值计算、审计编排和风险闸门 |
| `docs/methodology-improvement.md` | 面向维护者的方法论演进说明 |
| `tests/methodology-audit-contract.tests.ps1` | 信号、触发、风险和稳定结构契约测试 |
| `tests/fixtures/methodology-audit-signals.json` | 完全脱敏的固定测试信号 |

新增路径键必须先进入 `.claude/shared/paths.md`；workflow 需要的路径同步进入 `.claude/shared/runtime-contracts.js`，禁止另行硬编码。

### Gitignored 私有数据

```text
data/methodology-audit/signals.jsonl
data/methodology-audit/state.json
output/methodology-audits/YYYY-MM-DD-light.md
output/methodology-audits/YYYY-MM-DD-deep.md
output/methodology-audits/YYYY-MM-DD-incident-{unit}.md
```

- `signals.jsonl` 是追加式脱敏信号账本。
- `state.json` 保存上次审计时间、运行次数、观察期和未解决异常。
- `output/methodology-audits/` 保存审计报告、候选修改和回放对比。

## 运行接入与用户体验

日反馈、周报、月报等任务按以下顺序运行：

```text
1. 生成并保存正常用户报告
2. 追加运行计数和可确定的 C 级信号
3. 用户明确评价输出时追加 A 级信号
4. 后续验证行动或洞察时追加 B 级信号
5. 检查时间和异常阈值
6. 未触发则静默结束
7. 触发时在用户报告完成后运行审计
```

审计完成后只显示一句维护提示，例如：

```text
🔧 已完成本月方法论轻审计：自动修复 1 项，2 项继续观察。
```

需要人工批准时显示：

```text
🔧 方法论审计发现 1 项需要你决定的结构性问题，已生成提案。
```

用户不需要在每次报告后评分。明确的自然语言认可、反驳、遗漏、重复和行动反馈可以转换为 A/B 级信号；含义不明确的反馈只标记为待澄清，不强行归因。

## 主项目与用户版边界

主项目拥有完整的信号导入、审计、风险裁决和方法论更新能力。

用户版只负责：

- 本地采集明确反馈。
- 本地聚合。
- 导出脱敏汇总。

用户版不得自行修改公共方法论。内测反馈流为：

```text
内测用户本地反馈
→ 本地聚合
→ 导出脱敏汇总
→ 维护者主项目导入
→ 纳入统一审计
```

相关能力需要通过 `packaging/zhiji-user-overlay/` 和现有导出流程维护，不直接双向手改 `zhiji-user/`。

## 自动修改前置条件

L1/L2 自动修改还必须满足：

- Git 工作区干净。
- `VERSION` 与 `PROJECT_STATUS.md` 当前版本一致。
- 没有另一项冲突的方法论修改正在观察。
- 不覆盖用户未提交改动。
- 固定测试和历史回放能够执行。
- 修改范围符合对应风险等级。

工作区不干净时，审计仍可完成，但自动修改降级为待执行提案。

## 版本与提交

通过验证的自动修改继续遵守现有发布流程：

```text
更新 .claude/ 运行真相
→ 同步测试、公开文档和用户版导出链路
→ 递增语义化版本
→ 更新 PROJECT_STATUS / CHANGELOG
→ 自动本地提交
```

同一次审计的 L1 改动合并为一个版本，避免连续制造碎片化版本。自动提交信息包含审计编号，例如：

```text
[方法论优化] 收紧 coach 与 therapist 的职责重叠 [audit-2026-08-01]
```

系统不自动推送。

## 错误处理与恢复

- 信号采集失败不影响当前日反馈或复盘，只记录警告。
- 单条信号损坏时隔离该条，不让整个账本失效。
- 审计中断时不更新上次成功审计时间。
- 候选补丁测试失败时精确反向撤销本轮未提交改动，不产生版本。
- 风险不明确时按 L3 处理。
- 工作区不干净时只生成报告，不修改文件。
- 自动提交失败时保留已验证改动并明确提示，不静默宣称完成。
- 自动修改在观察期明显恶化时标记“建议回退”，展示影响范围并等待确认，继续遵守项目现有回退规则。
- 长期没有用户反馈时，时间审计只检查确定性问题，不推断内容质量已经改善。

## 分阶段交付

### 第一期：可观测

建立信号契约、私有信号账本、状态文件、明确反馈采集、内测脱敏汇总格式和手动审计入口。目标是证明系统能够捕捉真实方法论问题，不自动修改方法论。

验收条件：

- 正常报告不因采集失败而中断。
- A/B/C 信号可正确写入并保持脱敏。
- 用户反馈可以定位到方法单元或明确标记无法归因。
- 内测汇总不包含身份和原文。

### 第二期：可判断

加入时间/异常双触发、风险分级、确定性契约测试、历史回放和审计报告。目标是证明系统能够区分执行偏差、样本问题和方法论缺陷，仍不自动修改运行真相。

验收条件：

- 月度、季度和异常触发能够被固定测试复现。
- C 级信号不能单独越过风险闸门。
- 同一问题在观察期内不会反复触发修改。
- 每个候选方案包含证据、反例、风险和验证方式。

### 第三期：可演进

开启 L1/L2 自动修改、版本更新、本地提交、真实使用观察和恢复流程。

验收条件：

- 自动修改只在干净工作区和充分证据下发生。
- L3 始终等待人工批准。
- 修改前后可以进行基线对比。
- 自动修改进入观察期，不能立即宣称成功。
- 失败候选不产生版本，已提交改动的回退继续要求确认。

三期必须顺序实施。只有前一期积累了真实运行信号并通过验收，才能开启下一期。

## 非目标

- 不建立后台常驻服务或外部定时平台。
- 不要求用户每次报告后评分。
- 不自动改变复盘六问一级标题。
- 不让用户版各自演化公共方法论。
- 不保存内测用户原文或身份信息。
- 不使用单次 GPT 自评分证明方法论已经改善。
- 不在第一期直接开启自动方法论修改。
