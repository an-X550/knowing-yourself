# 本地飞书每日反馈入口设计

## 结论

先把现有「知己 CLI」应用扩成仅供本人使用的飞书私聊入口，在当前 Windows 电脑上持续运行一个薄适配进程。用户从手机发送带 `日志：` 前缀的单条文本后，适配进程只负责身份校验、防重、调用 Codex 非交互模式和回复消息；日志分析、文件写入、验证沉淀、飞书文档及滴答分发继续执行知己现有运行契约。

本阶段用于验证手机入口是否真的提高每日闭环频率，不购买云服务器，不迁移周/月复盘和主题思考，不重写分析引擎。电脑只需开机、不睡眠并联网，显示器可以关闭，Codex 桌面应用无需保持打开。

## 要解决的真实问题

用户认可知己每日分析的受控输出、证据约束、非讨好立场和跨日验证价值，但当前每次必须打开电脑、启动 Agent 应用并手工发送日志，约 4–5 分钟的启动成本会阻断高频使用。通用手机 AI 不能稳定复现知己的输出契约，因此单纯换一个手机对话工具不能解决问题。

成功标准不是“拥有一个飞书 BOT”，而是：

> 用户在手机粘贴日志后，无需操作电脑即可得到与当前知己契约一致的每日反馈，并留下可供后续周/月复盘消费的同一份本地数据。

## 必要性闸门

该需求通过新增功能必要性闸门：

1. **当前具体证据**：每日 4–5 分钟启动成本已经阻断实际使用，不是未来假设。
2. **直接服务核心目标**：它缩短“记录 → 洞察 → 行动 → 次日验证”的最高频闭环。
3. **更小替代路径不足**：通用手机 AI 无法稳定执行现有证据、结构和行动契约；完整云化则明显过重。
4. **可以立即验证**：手机发送日志后，可核对本地文件、反馈内容、分发结果、防重和真实使用次数。

## 方案比较

### 方案 A：Windows 本地薄入口（采用）

复用当前项目、个人数据、Codex 登录和结果分发配置，只增加飞书消息适配进程。开发量和数据迁移成本最低，也最容易排错。代价是电脑关机、睡眠或断网时不可用。

### 方案 B：直接部署云服务器（暂缓）

可以真正全天候使用，但必须迁移个人数据、凭据和运行环境，并解决本地周/月复盘的数据同步。当前尚未证明用户会高频使用手机入口，不值得先承担这些成本。

### 方案 C：调用通用手机 AI（拒绝）

几乎没有开发成本，但不能可靠复用知己的分析契约、验证沉淀和防重状态，失去项目的核心价值。

## 范围

### 第一版必须支持

- 复用现有「知己 CLI」飞书应用，一个 BOT，不新建多个机器人。
- 只接受已绑定用户在与 BOT 单聊中发送的纯文本。
- 只识别明确前缀 `日志：`；前缀后的全部内容按原文进入现有日志链路。
- 运行现有日志存档和每日反馈流程，包括 A–D 证据等级、昨日闭环、单洞察、单行动与结构校验。
- 继续以当前电脑中的 Markdown 为唯一权威数据源。
- 新反馈写入成功后，继续执行现有飞书与滴答分发规则。
- 把每日反馈正文和实际分发摘要回复到原飞书私聊。
- 同一飞书 `message_id` 最多处理一次；相同日期已有反馈时执行现有快路径，不伪装成新写入。
- 给用户返回明确的成功、补证或失败结果，不静默丢弃。

### 第一版明确不做

- 周复盘、月复盘、项目复盘、主题思考、收藏资料的飞书消息入口。
- 群聊、其他用户、多租户、邀请机制或管理后台。
- 图片、语音、文件附件或多日批量日志。
- 云服务器、数据库、Redis、消息队列、监控平台或网页界面。
- 自动开机、远程唤醒电脑或离线消息补偿队列。
- 新的分析提示词、报告结构、输出目录或第二套分发逻辑。
- 飞书知识问答；文档检索继续使用飞书现有能力。

## 架构与职责

```text
飞书私聊消息
  → 飞书 Channel SDK（长连接、事件解析、基础去重与回复）
  → 本地入口适配器（本人白名单、前缀校验、业务防重、串行执行）
  → Codex 非交互运行（项目根目录、workspace-write）
  → 知己现有日志与 daily-review 契约
  → 本地日志 / 每日反馈 / verified-patterns / 分发状态
  → 飞书文档 + 滴答任务（仅按现有契约）
  → 飞书私聊回复
```

### 飞书 Channel SDK

只负责建立长连接、接收单聊消息、提供规范化消息对象并回复。启用应用机器人的最小消息权限与 `im.message.receive_v1` 事件，不扩大云文档目录和其他飞书资源权限。

### 本地入口适配器

这是本轮唯一新增的运行组件，职责严格限制为：

1. 校验消息来自配置中唯一允许的用户 `open_id`。
2. 拒绝群聊、机器人消息、非文本和无 `日志：` 前缀的内容。
3. 以 `message_id` 做入口防重，并保证同一时间只运行一个每日反馈任务。
4. 从项目根目录调用 Codex 非交互模式，不自行解释或改写日志。
5. 读取最终执行结果并回复原会话，不从命令日志拼凑成功状态。

### Codex 非交互运行

适配器调用官方 `codex exec`，使用当前机器已经保存的 Codex CLI 身份，工作目录固定为知己仓库根目录，沙箱使用 `workspace-write`。传给 Codex 的指令明确声明这是一次运行型日志请求，并附原始飞书文本；由现有 AGENTS、日志路由和每日反馈契约决定读写与分发。

实现前必须先在当前 Windows 用户会话中完成一次非交互预检。若 Codex CLI 不可执行、未登录或不能在项目目录完成受控写入，停止实施并报告真实错误；不得悄悄切换到另一模型或复制一套提示词冒充当前项目能力。

### 现有知己运行时

`.claude/` 继续是唯一运行真相。入口适配器不解析 `daily-analyzer` 输出、不直接写日志和反馈、不手工调用飞书或滴答；所有业务动作都由现有日志入口、`daily-review` 和结果分发契约完成。

## 消息与数据流程

1. 用户在手机私聊 BOT，发送 `日志：<原文>`。
2. Channel SDK 收到消息并交给入口适配器。
3. 适配器依次检查：单聊、发送者白名单、文本类型、明确前缀、非空正文、`message_id` 未成功处理。
4. 校验通过后，把该 `message_id` 标为处理中，并回复简短受理消息。
5. 适配器从项目根目录串行执行一次 `codex exec`，要求按当前日志入口保存并分析这条日志。
6. Codex 按现有契约确定日期；日期不可靠或输入为 D 级时，只返回一个补证问题，不写正式反馈。
7. 正式反馈写入、复读、验证沉淀与结果分发由现有流程完成。
8. 适配器只在 Codex 正常终止且最终消息存在时，把最终消息回复到原会话，并将入口状态记为成功。
9. 执行失败时把状态记为失败，回复一条简短错误和“可明确重试”的提示；不把失败记录当成成功防重证据。

## 状态与防重

入口新增一个 gitignored 的最小状态文件，只记录：

- `message_id`
- `received_at`
- `status`: `processing` / `success` / `failed`
- 规范化错误分类
- 对应目标日期（只有现有流程可靠返回时记录）

状态不保存日志正文、反馈正文、访问令牌、命令行或完整 stdout/stderr。

防重分两层：

- **入口层**：同一 `message_id` 成功后再次收到，只回复“已处理”，不再调用 Codex。
- **业务层**：同一日期已有反馈时继续由现有 `daily-review` 快路径和结果分发 SHA 状态处理，入口不绕过、不覆盖。

异常退出后遗留的 `processing` 只提示“上次处理未确认完成”，不自动重跑。用户明确再次发送新消息才形成一次新请求；已有本地结果仍由业务快路径阻止重复副作用。

## 安全与隐私边界

- 只允许配置中唯一 `open_id`，默认拒绝其他发送者。
- 只处理与 BOT 的单聊，不加入群聊、不读取聊天历史。
- 只把当前消息正文交给知己；不下载附件、不扫描飞书或电脑寻找输入。
- 飞书 App Secret、Codex 身份和其他凭据只使用各自项目外的官方凭据存储或用户级环境，不进入仓库和入口状态。
- `codex exec` 固定在仓库根目录并使用 `workspace-write`；入口不得开放任意 prompt、shell 命令、路径或目标 token。
- 用户日志中的指令性文本被视为个人日志内容，不得改变入口适配器权限和调用边界。
- 非本人消息、群聊消息和不支持的类型不调用 Codex，也不产生任何本地或外部副作用。

## 运行与可用性

验证期不把适配器注册为系统级 Windows 服务，先提供一个明确的启动命令，在当前用户会话中运行。这样排错和停止都更直接，也避免首版增加安装器与服务账户权限问题。

运行条件：

- Windows 电脑开机且用户会话可用。
- 系统关闭自动睡眠；显示器可以按原设置关闭。
- 网络能够访问飞书和 Codex 所需服务。
- 飞书适配器进程与 Codex CLI 身份均可用。

进程停止、电脑睡眠、关机或断网时，BOT 不承诺即时响应。首版不排队、不远程唤醒；用户可在电脑恢复后重新发送日志。

## 错误处理

| 场景 | 行为 |
|---|---|
| 非本人或群聊消息 | 拒绝，不调用 Codex，不写状态正文 |
| 无前缀或正文为空 | 返回固定使用说明，不调用 Codex |
| 日期不明确 / D 级输入 | 返回现有流程的唯一补证问题，不生成反馈 |
| Codex CLI 不可用或未认证 | 返回 `runtime_unavailable`，保留原始技术证据在本机运行日志，不产生业务副作用 |
| 分析或本地写入失败 | 返回失败；不调用结果分发 |
| 飞书或滴答分发失败 | 保留本地成功，按现有契约分别报告渠道结果 |
| 回复飞书失败 | 本地结果和分发状态保持不变；标记 `reply_failed`，不重新分析 |
| 重复 `message_id` | 已成功则只回复已处理；处理中或未知终态不自动重跑 |

连续遇到同一根因 3 次时停止试验并保留证据，不继续增加重试、队列或替代执行路径。

## 验收

### 技术验收

1. 非交互预检：从仓库根目录运行受控只读任务，证明 Codex CLI 身份和项目上下文可用。
2. 通道验收：本人手机私聊能收到回声；其他账号、群聊和非文本不进入业务处理。
3. 脱敏端到端：一条受控日志产生一个本地日志、一个结构合格的每日反馈，以及按正式配置产生的飞书和滴答结果。
4. 正文一致：聊天回复与本地反馈正文一致；外部分发不改写本地正文。
5. 防重验收：重复投递同一消息不重新运行；再次查看同日反馈不重写文件、不新建飞书文档或滴答任务。
6. 失败验收：模拟 Codex 不可用或写入失败，只返回失败，不产生半成品分发。

### 真实使用观察

连续观察 14 天，不把受控测试计入：

- 手机提交真实日志至少 10 次。
- 从发送到收到反馈的用户操作时间低于 1 分钟；模型等待时间单独记录。
- 至少 7 次对反馈行动作出“执行、明确拒绝或证据不足”的真实记录。
- 没有重复本地反馈、飞书文档或滴答任务。
- 电脑在线条件没有成为新的主要摩擦。

达到上述条件后，才评估把同一进程迁移到云服务器；未达到则停止，不扩展周/月/主题入口。

## 后续迁移边界

本地验证成功只证明手机入口有价值，不自动授权购买服务器或迁移数据。未来云迁移必须单独设计数据权威来源、凭据、备份与本地周/月复盘同步；不得在本轮代码中预建多环境、数据库抽象或云部署框架。
