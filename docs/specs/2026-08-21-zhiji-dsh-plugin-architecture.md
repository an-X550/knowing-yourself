# 知己 DeepSeek Harness 独立插件架构

## 1. 架构结论

新路线不是把知己桌面端改造成 DeepSeek Harness（DSH）插件平台，而是把知己已经形成的复盘能力制作成一个独立 DSH Bundle：

- 知己桌面端继续使用现有 Electron、React、Main Process、固定 DSH Runtime 和专业页面，面向希望打开即用的普通用户。
- `zhiji-dsh-plugin` 面向已经安装 DSH 的用户，使用 DSH 官方 Profile/Bundle、Agent Runtime、审批和 Web UI。
- 插件以当前阶段的知己复盘能力为参考完成一次独立转化，不共享前端外壳、宿主生命周期和安装系统，也不要求此后与桌面端实时同步源码。
- 插件不修改或 fork DSH 源码，不复制 Loader、Profile、HMR、inventory 和包管理；安装、更新、移除继续交给官方 `dsh plugin`/pnpm。
- 第一版只证明一个“每日复盘”能力可以独立安装、运行和移除。周/月/项目复盘、文件目录适配和公开发布必须分别用前一阶段证据决定。

这条路线把 DSH 当作现成发行平台，而不是把知己变成第二个 DSH。

## 2. 第一性原理复核

### 2.1 真正要解决的问题

真正问题是：

> 如何用最低的新增成本，把知己已经验证过的中文日志复盘能力提供给现有 DSH 用户，同时不破坏知己桌面端的普通用户体验，也不维护第二套 Agent 平台。

因此，“拥有插件系统”“使用 DSH Web UI”“发布 npm 包”都只是可能的手段。只有当一个 DSH 用户能安装知己能力并完成一次有价值的复盘时，路线才产生产品价值。

### 2.2 已知事实

- 知己桌面端已经有稳定的日志、每日反馈、周/月/项目复盘、正式写入和 Agent 会话链路，不需要为了发布插件重写。
- P0 已验证 DSH rc.8 的 Profile、Bundle、Loader、配置 HMR、只读 inventory 和 `dsh plugin` 包管理路径；Bundle 成员变化仍以 Profile 重启为边界。
- DSH 官方 Web UI 已经承担对话、工具活动和插件客户端扩展；第一版知己插件没有证据需要自定义 Web UI。
- DSH Bundle 可以作为仓库外 package 安装到 Profile，不需要修改 DSH 源码。
- DSH 插件是 Node 宿主代码。知己自己发布的插件可以建立明确来源和版本信任，但仍要处理 DSH 兼容、Node 依赖和数据访问边界。
- 当前 `.claude/` 中的 Skill、agent 和共享契约是知己复盘方法的运行真相；桌面端通过自己的结构化实现提供同等产品行为。

### 2.3 未验证假设

- DSH 用户是否愿意用知己方法完成中文日志复盘。
- “粘贴日志 → 每日复盘 → DSH 会话结果”是否已经足够有价值，还是必须读取文件目录。
- DSH 插件能否直接复用现有 Skill 形态，还是需要少量 Host Tool 才能形成稳定输入输出。
- 周、月、项目复盘是否值得作为同一插件的后续能力，而不是由用户继续使用知己桌面端。
- 插件是否会形成独立用户、版本和发布节奏，从而值得拆成独立仓库。

这些假设由 S1 及后续阶段逐个验证，不在架构文档中提前写成事实。

### 2.4 不可突破约束

- 不修改、复制或 fork DSH 源码以实现插件。
- 不替换、迁移或删除知己桌面端 React 前端和固定 Runtime。
- 插件运行时不依赖知己桌面端、Electron Main Process 或当前仓库绝对路径。
- 第一版不提供自定义 DSH Web UI、插件市场、通用 Shell、代码编辑或任意系统自动化。
- 插件不把 DSH 的模型、会话、审批、Profile 和安装能力重新实现一遍。
- 插件不能在发布说明中宣称与桌面端完全等价；对用户有影响的差异应写清适用入口，但不建立跨项目强制同步门禁。

### 2.5 价值取舍

- 先共享规格，再共享代码：少量重复适配优于提前抽取大型公共 SDK。
- 先支持人工粘贴材料，再支持目录读取：用最小输入链路验证复盘价值。
- 先使用 DSH Web UI，再评估自定义 UI：避免重新建设前端。
- 先用本地预构建 tarball 验证，再发布 npm：避免把分发成功误当作产品成功。
- 产品和发行边界现在独立；物理仓库是否拆分等 S1 后再决定。

## 3. 两个产品的职责边界

| 能力 | 知己桌面端 | 知己 DSH 插件 |
|---|---|---|
| 目标用户 | 不熟悉 Agent 工具、希望打开即用的用户 | 已经安装并使用 DSH 的用户 |
| 产品界面 | 知己 React 专业页面 | DSH Web UI；第一版不新增客户端插件 |
| Agent 宿主 | 现有 Electron Utility 固定 Runtime | 用户已有 DSH Profile |
| 安装升级 | 知己桌面应用发布链路 | 官方 `dsh plugin`/pnpm |
| 日志输入 | 知己日志页面与数据目录 | 第一版粘贴；后续可配置只读日志目录 |
| 每日/周期复盘 | 专业任务和正式产物 | Skill/Tool 驱动的会话结果 |
| 正式存储 | 知己仓储、备份、恢复和回收站 | 第一版不拥有知己正式仓储 |
| 插件生态 | 不开放社区插件安装 | 自身就是一个 DSH 插件，不管理其他插件 |
| 安全边界 | Main/Preload/Renderer/Utility 分层 | DSH Host code 信任模型和 Profile 边界 |

两个产品可以功能相似，但不要求界面和存储行为完全同构。桌面端提供完整产品闭环；插件提供可嵌入 DSH 的复盘能力。

## 4. 目标架构

```text
               当前知己能力参考快照
       Skill / Prompt / Schema / 示例 / 输出契约
                         │
             ┌───────────┴───────────┐
             │                       │
             ▼                       ▼
     知己桌面端适配              zhiji-dsh-plugin
  Electron Main/Utility           DSH Bundle package
  React 专业页面                  Skill / Host Tools
  知己正式仓储                    Prompt sections
             │                       │
             ▼                       ▼
      知己桌面产品               用户已有 DSH Runtime
                                      │
                                      ▼
                                  DSH Web UI
```

### 4.1 当前能力参考快照

插件开发开始时，从当前知己能力中选择本阶段需要转化的部分作为参考：

- 输入材料的最低要求和证据降级规则；
- 每日、周、月、项目复盘的分析边界；
- 单一洞察、单一行动和后续验证语义；
- 输出字段、Markdown 结构和错误语义；
- 用于防止两端漂移的代表性 fixture。

现阶段可参考现有 `.claude/` Skill、agent 和 shared contract，但插件发布物必须自包含，不能在用户机器上读取知己仓库的 `.claude/` 路径。转化完成后，桌面端和插件可以按各自用户需求独立演进；本路线不建设自动同步、代码生成、双向镜像或跨项目一致性检查工具。

### 4.2 DSH Bundle 适配层

插件应优先采用 DSH 官方公开扩展面：

- `package.json` 声明 `dsh.bundle.patch`；
- `cordis.patch.yml` 把插件需要的 entry 插入 DSH Profile；
- Skill 能表达的分析方法继续用 Skill；
- 只有需要稳定解析、材料聚合或结构化结果时才增加 Host Tool；
- system-prompt section 只承载对所有插件会话都必要的短规则，不复制完整 Skill；
- 插件设置只保留无法通过会话输入解决的少量配置。

具体 package 名、目录和 DSH API 以 S1 对 rc.8 公开入口的实测为准。本文冻结职责，不冻结未经实现验证的代码形状。

### 4.3 DSH Runtime 与 Web UI

DSH 继续负责：

- 模型、Agent loop、会话和上下文；
- Tool/Skill 注册与生命周期；
- Profile、Bundle、配置 HMR 和重启；
- Web UI、工具活动展示和用户审批；
- `dsh plugin` 安装、更新和移除。

知己插件不再包装 DSH Web UI，也不发布 DSH 桌面壳。社区已经存在的非官方桌面发行版与本项目没有运行依赖。

## 5. 插件能力范围

### 5.1 S1 最小能力

S1 只实现每日复盘：

1. 用户在 DSH 对话中粘贴一段单日日志或明确提供日志材料。
2. Agent 调用知己 Skill/Tool 分析材料。
3. 返回符合知己每日反馈核心契约的结构化 Markdown。
4. 用户可以继续在同一 DSH 会话讨论，但第一版不自动写入知己数据目录。

这条链路足以验证“知己能力作为 DSH 插件是否有价值”，不需要先完成文件读取、周期聚合或发布市场。

### 5.2 后续候选能力

只有 S1 验收通过后，才按证据考虑：

- 周复盘、月复盘和项目复盘；
- 配置日志目录和日期范围聚合；
- 经用户确认保存 Markdown 报告；
- 与知己桌面数据格式的只读兼容；
- DSH headless 场景。

### 5.3 不移植的桌面能力

- React 日志、复盘、项目和设置页面；
- Electron 窗口、IPC、preload 和本地凭据；
- 知己备份、恢复、迁移和回收站；
- 桌面端导航卡和页面跳转；
- 当前固定 DSH Runtime 的 Main Process 工具桥；
- 桌面端专用任务进度和正式产物管理。

## 6. 输入、输出与数据边界

### 6.1 第一版输入

第一版优先接收会话内明确材料，避免把文件系统配置作为价值验证的前置条件。插件需要区分：

- 用户提供的日志正文；
- 用户对分析范围和目标的说明；
- DSH 会话历史；
- 缺失材料时的降级提示。

不得在用户未指明的情况下扫描整个工作区、家目录或知己桌面数据目录。

### 6.2 第一版输出

结果直接进入 DSH 会话，并保持知己的核心质量约束：

- 事实、推断和建议分开；
- 输入不足时降级，不补完整故事；
- 聚焦一个主要洞察和一个可验证行动；
- 不把聊天自由发挥冒充知己正式存档。

### 6.3 后续文件适配

如果 S1 证明用户确实需要读取长期日志，优先增加一个显式配置的只读根目录：

- 路径由用户选择或配置；
- 只读取明确支持的 Markdown；
- 日期和范围解析有确定性测试；
- 错误不会回退为任意目录搜索；
- 默认不与知己桌面端同时写同一文件。

写入能力必须另行说明写入目标、覆盖/并发语义和恢复方式，不能作为“顺手补齐”。

## 7. 转化与独立演进策略

### 7.1 以当前能力为参考转化

S1 不要求先提取通用 `review-core`，也不要求插件直接引用桌面端或 `.claude/` 源文件。实现时参考：

- 每日反馈 Skill 和 agent 规则；
- prompt-rules 中与每日反馈直接相关的契约；
- 代表性输入/输出 fixture；
- 证据降级、行动和验证规则。

插件可以针对 DSH 会话体验重新组织这些能力。只要名称、README 和用户提示不把差异版本冒充为桌面端完全同构，就不要求逐文件或逐输出一致。

### 7.2 默认不抽取共享代码

当前路线默认不抽取共享包、不写同步脚本。只有未来两个项目都出现明显维护痛点，并且用户重新确认值得处理时，才另行评估纯领域模块，例如：

- Markdown 日志解析；
- 日期范围计算；
- 材料聚合；
- 输出 Schema 校验。

这不是 S1-S4 的组成部分。Prompt 和 Skill 文本不因“代码复用”被强行改造成复杂 DSL。

### 7.3 允许独立演进

桌面端和 DSH 插件的宿主、用户和发布节奏不同，允许存在差异，例如：

- 桌面端保存正式报告，插件第一版只返回会话结果；
- 桌面端有专业页面，插件使用 DSH Web UI；
- 桌面端固定 Runtime，插件依赖用户 DSH Profile。

差异只需在影响安装、输入、输出或数据安全时对用户说明，不以源码、测试数量、输出逐字或版本同步作为验收目标。

## 8. 安装、版本与发布边界

### 8.1 开发验证

S1 优先使用本地、预构建、无安装脚本、无 native dependency 的 tarball 或 directory fixture，并安装到临时 `DSH_HOME`。不在开发初期依赖公开 npm 名称和真实用户 Profile。

### 8.2 正式分发

只有 S1/S2 形成可用能力后，才选择 npm 或 GitHub Release tarball：

- 包含构建产物；
- 固定并公开已验证的 DSH 版本；
- 不要求用户允许 Git `prepare` 脚本；
- README 给出 add、update、remove 和 Profile 重启说明；
- 使用 GitHub `dsh-plugin` topic 只表示可发现，不表示官方审核。

### 8.3 版本策略

- 插件拥有独立版本，不与知己桌面端版本强绑定。
- 每个插件版本记录已验证的 DSH 精确版本或兼容范围。
- DSH rc 发生变化时先跑兼容测试，再更新声明。
- 不通过复制上游代码来冻结行为；不兼容时可以保持旧插件版本或等待上游稳定。

## 9. 信任与安全边界

本路线只发布知己自己的 DSH 插件，因此不承担“知己替用户审核所有社区插件”的平台责任。但仍需遵守：

- 插件代码按 Node 宿主代码对待，不宣称被 Agent sandbox 隔离；
- 第一版不读取凭据、不创建子进程、不注册 Shell、不加载 native module；
- 网络能力只有出现明确产品需求时再增加，并说明访问目标；
- 不在安装阶段执行来源不明脚本；
- 不收集或上传用户日志；
- DSH 用户选择安装代表信任知己插件，不代表知己桌面端开放第三方插件。

## 10. 仓库与项目边界

`zhiji-dsh-plugin` 从第一天起就是独立发行物：它应有自己的 package manifest、版本、README、测试和构建产物。

是否立即拆成独立 GitHub 仓库不是架构前提。高性价比默认是：

1. S1 在当前仓库的独立 package/工作目录中验证，减少同步和发布治理。
2. 插件运行时不得依赖仓库内相对路径，保证可随时单独打包；不要求建立与知己项目的自动同步机制。
3. 当插件需要独立发布、Issue、贡献者或版本节奏时，再拆为独立仓库。

如果执行前用户已经建立独立仓库，也可以直接在那里实现；只要仍以版本化规格和 fixture 防止复盘语义漂移即可。

## 11. 分阶段架构裁决

| 阶段 | 目标 | 当前裁决 |
|---|---|---|
| S0 | 新路线架构和执行规划，旧路线标记被取代 | 本文完成 |
| S1 | 一个可安装、可运行、可移除的每日复盘 Bundle | 待用户单独确认后执行 |
| S2 | 周/月/项目复盘能力扩展 | 仅在 S1 证明价值后 |
| S3 | 显式日志目录、范围聚合和可选保存 | 仅在出现文件使用需求后 |
| S4 | 独立发布、兼容矩阵和用户安装文档 | 仅在插件能力可用后 |
| 自定义 DSH UI | 插件专用页面或复杂卡片 | 暂不规划 |
| 知己桌面插件平台 | 安装和管理任意 DSH 插件 | 已取消 |

## 12. 整体完成标准

新路线只有满足以下事实才可称为“知己 DSH 插件”：

- 插件作为仓库外 Bundle 通过官方 DSH Profile 机制安装，不修改 DSH 源码。
- DSH 用户无需安装知己桌面端即可完成至少一次有效复盘。
- 插件使用 DSH Web UI，不复制桌面 React 页面。
- 插件可以通过官方命令移除，移除后 Profile 仍可启动。
- 知己桌面端代码和默认 Runtime 不因插件发行物发生行为回退。
- 每个对外能力有自己的可复跑验证样例，并且没有把已知差异宣传为桌面端等价能力。
- 实现没有自建 Loader、Profile、包管理器、市场或通用 Agent 平台。

## 13. 停止与降级条件

以下情况出现时，优先缩小或停止插件路线：

- 必须 fork/修改 DSH 源码或依赖内部 deep import 才能加载；
- 每日复盘必须复制大量桌面基础设施才能工作；
- 插件必须依赖知己桌面端运行或读取其私有 IPC；
- DSH Web UI 无法承载最小复盘交互，且自定义 UI 成本接近再做一个产品；
- DSH rc 兼容维护持续高于插件实际使用价值；
- 没有用户或真实使用情境，只有“已经做了插件”的简历目标；
- 为统一两端而大幅重构已经稳定的桌面端。

停止插件路线不影响知己桌面端，也不否定 P0 的技术验证价值。
