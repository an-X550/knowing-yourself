# 知己桌面端接入 DeepSeek Harness 的 Agent 架构

## 1. 决策结论

知己桌面端采用“**现有产品内核与专业页面不变，DeepSeek Harness（DSH）作为上层 Agent 编排器**”的混合架构。DSH 不替代日志、复盘、项目、主题、备份等领域能力，不直接读写知己文件，也不使用 DSH 原生 Web UI 作为产品主界面。

最终职责只有两条：

- DSH 决定为了完成用户目标，需要理解什么、调用哪些能力、按什么顺序继续。
- 知己领域服务决定哪些数据可读写、结果是否合规、何时需要既有确认、最终如何保存和展示。

这不是在现有桌面端旁边增加一个聊天机器人，而是让自然语言会话成为能够调用现有产品能力的第一等入口。

## 2. 第一性原理判断

### 2.1 真正问题

当前桌面端已经能完成日志、日反馈、周期复盘、主题思考和项目管理，但这些能力由页面和固定工作流分别触发。系统没有统一会话、跨能力的工具选择、连续多步执行和基于执行结果继续判断的 Agent Runtime。

目标不是“使用热门框架”，而是同时满足：

1. 用户可以用自然语言表达目标，不必先理解功能入口。
2. Agent 可以组合已有能力完成多步任务，而不是只做一次分类或一次模型调用。
3. 现有结构化报告、确认边界、本地数据和专业页面继续可靠工作。
4. 新架构仍服务“发现模式 → 形成行动 → 后续验证”，不把聊天本身当作产品价值。

### 2.2 为什么不是恢复旧意图路由

2026-08-14 删除的首页意图路由只负责“输入一句话 → 跳转页面”，与已有导航重复。新的 Agent 入口必须能够读取上下文、调用工具、等待结果、继续下一步并保留会话；如果最终仍只做页面跳转，应停止 Agent 化并继续使用现有导航。

### 2.3 为什么选择 DSH

DSH 提供本项目缺少的通用 Agent loop、会话事件、工具注册、模型适配和插件组合。知己无需再次开发一套通用 Harness，只需把领域能力接入它。选择 DSH 是为了复用编排基础设施，不代表把产品逻辑迁入第三方框架。

## 3. 目标架构

```text
Electron Renderer（现有 React 主界面）
├─ 开始 / 日志 / 复盘 / 主题 / 项目 / 设置
└─ Agent 页面：会话、执行过程、结果卡片、跳转
        │ window.zhiji.agent.*
        ▼
Preload + Main Process
├─ AgentFacade：会话生命周期、取消、事件转发
├─ AgentToolDispatcher：校验并调用现有应用服务
├─ ModelTransport：持有解密后的 API Key，代理模型网络请求
└─ 现有知己产品内核
   ├─ application / domain / repositories
   ├─ LangGraph 日反馈与周期复盘
   ├─ Schema、确定性渲染、确认和写入
   └─ 数据目录、备份、回收站、safeStorage
        │ Electron MessagePort
        ▼
Electron Utility Process
└─ 自定义 DSH Runtime
   ├─ Agent loop 与 session events
   ├─ 知己 system prompt / preset
   ├─ 受限的知己工具注册
   └─ 不挂载通用文件系统、Shell 和任意命令工具
```

### 3.1 为什么使用 Utility Process

不把 DSH 直接装进 Renderer，也不默认与 Main Process 同进程：

- Renderer 必须继续保持 `nodeIntegration: false`、`contextIsolation: true` 和 `sandbox: true`。
- DSH 的循环、插件或异常不应拖垮文件、备份和窗口生命周期所在的 Main Process。
- Utility Process 可使用 Node 运行 DSH，又能通过 Electron MessagePort 与宿主双向通信，不需要开放 localhost HTTP 端口。
- Main Process 仍是本地文件、系统能力和密钥的唯一持有者。

如果实测 DSH 依赖无法运行于 Utility Process，才降级为由 Main Process 启动的受控 Node 子进程；不因此改用浏览器 Web UI。

## 4. 能力保留与取舍

| 当前能力 | 决策 | Agent 化后的职责 |
|---|---|---|
| React 页面与 AppShell | 保留并优化 | 增加 Agent 一级页面和结构化结果跳转，不重写现有专业页面 |
| Electron Main/Preload/IPC | 保留并扩展 | 新增 `agent.*` 契约和进程消息桥 |
| 日志、项目、模板、个人背景 | 保留 | 通过领域工具访问，禁止 DSH 直接操作文件 |
| 日反馈、周/月/项目复盘 | 保留 LangGraph 与确定性渲染 | 作为高层工具供 Agent 调用，不把严格报告改成自由聊天输出 |
| 日志质量、年度回顾、方向校准 | 保留 | 继续走材料预览和现有应用服务 |
| 主题正文与确认沉淀 | 保留 | DSH 负责对话；知己负责归纳提案、确认和主题仓储 |
| 验证模式候选与确认 | 保留 | Agent 可提出调用，仍由现有服务约束“候选不落库、确认才沉淀” |
| safeStorage 与服务商设置 | 保留 UI 和密钥边界 | DSH 不建立第二套明文凭证或设置真相 |
| 备份、恢复、回收站 | 保留 | Agent 会话纳入数据生命周期；删除仍使用既有确认与回收站语义 |
| 受控联网 | 保留并工具化 | 复用 URL、sourceId 和会话绑定限制，不给 DSH 任意网络工具 |
| DSH 原生 Web UI | 不采用 | 当前 React 是唯一产品主界面 |
| DSH 通用文件/Shell 工具 | 不注册 | 知己不是编码 Agent，直接文件或命令权限没有产品必要性 |

## 5. 无法原样保留的部分

### 5.1 单次 Provider 不再是唯一 AI 运行方式

现有 `ProviderPort.collect/stream` 继续服务严格工作流，但 Agent 对话必须进入 DSH 的多轮模型—工具循环。两条路径可以并存，不能把一次模型调用伪装成 Agent Runtime。

模型密钥继续由 Main Process 的 `ConfigureAi` 与 `safeStorage` 持有。DSH 使用宿主提供的模型传输接口，不直接读取凭证文件；模型、超时和错误最终仍映射为知己的公开配置与中文错误。

### 5.2 Skill 规则保留，原运行方式不保留

`.claude/` 继续是产品逻辑权威，但打包后的桌面端不能在运行时依赖仓库路径。实施时从选定的共享契约和兼容快照生成版本化 Agent bundle，供 DSH preset、system prompt 和工具说明使用；不得人工维护第二份无来源提示词。

DSH 不被假定能原样执行 Claude Skill。能复用的是规则、提示词和工具语义，不是 Claude 的发现与调用协议。

### 5.3 主题临时会话需要迁移

DSH session event log 成为 Agent 对话的过程真相；`TopicRepository` 继续保存用户确认后的长期认识。现有 `TopicSessionStore` 不应长期与 DSH 重复保存同一种对话。

旧主题会话必须可读取：用户恢复旧会话时，将旧消息导入一个新的 DSH session，原文件保留到新会话成功创建；之后停止创建新的旧格式会话。不得静默丢弃或要求用户手动复制。

### 5.4 进度与取消协议需要统一

现有复盘阶段进度继续显示；Agent 页面另外消费 DSH 的 turn、step、tool call 和完成事件。`AgentFacade` 把两者归一为前端可理解的结构化事件，但不伪造百分比。取消 Agent turn 必须向 DSH 传播，工具已进入现有 `ReviewTaskManager` 时还要继续传播其 AbortSignal。

## 6. Agent 工具设计

### 6.1 工具按用户目标而不是仓储方法设计

首批工具使用稳定的领域动作：

- 日志：列出、读取、创建、更新。
- 反馈与复盘：生成日反馈；预览和生成周/月/项目复盘；预览和生成洞察工具。
- 项目：列出、创建、重命名、归档、恢复。
- 主题：读取相关主题、提出归纳、确认沉淀。
- 模式：列出、提出候选、确认候选。
- 联网：搜索、读取该次搜索返回的来源。
- 界面：请求前端导航至已有页面或结果对象。

设置、备份恢复、数据目录迁移、批量删除和任意文件操作不作为首批模型工具。这些能力已有清晰页面，Agent 介入不会提高洞察或闭环质量。

### 6.2 写入规则沿用现有业务语义

不增加统一的“所有写入都确认”门。工具是否执行由当前具体业务决定：

- 用户明确要求记录日志时，可直接调用现有创建服务。
- 周/月/项目复盘继续执行现有材料预览与确认。
- 主题和验证模式继续由用户确认后沉淀。
- 删除继续使用现有 UI 确认和回收站，不开放为普通 Agent 工具。

工具入参必须经过共享 Zod Schema；工具不得返回本地绝对路径、API Key 或超出任务需要的完整个人材料。

## 7. 前端优化设计

### 7.1 保留专业页面，新增 Agent 工作区

一级导航增加“知己 Agent”。Agent 页面包含：

1. 会话列表与新建会话。
2. 对话正文，继续使用安全 Markdown 渲染。
3. 当前步骤与工具活动卡，只显示用户可理解的动作和结果。
4. 结构化结果卡，例如“已生成 8 月周复盘”，可跳转现有复盘页。
5. 停止当前任务和继续输入。

不在所有页面重复放置大型聊天框。现有开始页仍负责确定性建议，Agent 页负责目标式、多步和连续对话，避免重新制造第四套导航。

### 7.2 Agent 不直接控制 DOM

DSH 只能产生受校验的 `ui.navigate` 或 `ui.present` 事件。Renderer 根据 `NavigationTarget` 决定是否跳转和如何展示；Agent 不执行前端脚本，也不持有 `window.zhiji`。

### 7.3 聊天与正式产物分离

聊天消息用于解释、澄清和汇报执行；正式日志、复盘、主题和模式仍进入原有页面与仓储。聊天气泡不能成为正式产物的唯一保存位置。

## 8. 会话、数据与安全

- DSH 会话保存在当前知己数据目录的 `agent/sessions/`，跟随存储位置迁移。
- 会话可以引用领域对象 ID，但日志和复盘正文仍以现有仓储为权威，避免复制后漂移。
- Agent 会话可能含个人内容，备份与恢复需将其作为已知业务类别校验；API Key 仍不进入备份。
- DSH 默认 profile 只装载知己需要的模型、session、agent loop 和领域工具插件，不继承面向编码场景的 Shell、终端、任意文件系统与工作区编辑能力。
- 所有 Renderer 输入仍经 Preload 具名 API 和 Main Process Schema 校验；Utility Process 的工具请求再次由 `AgentToolDispatcher` 校验，不能因为来自本机子进程而信任。

## 9. 实施阶段

### 阶段 A：运行时与会话桥

- 引入 DSH Runtime 与 Utility Process 生命周期。
- 建立 `agent.start/send/cancel/list/get` IPC 和 session event 流。
- 完成模型传输适配、中文错误映射和应用退出清理。
- 新增 Agent 页面，但暂不移除任何现有入口。

### 阶段 B：只读上下文与结果导航

- 接入日志、复盘、项目、主题和验证模式的只读工具。
- 接入 `ui.navigate/ui.present`，结果跳转现有页面。
- 验证 Agent 不依赖原始文件路径和通用文件系统工具。

### 阶段 C：高层工作流工具

- 接入日反馈、周期复盘和洞察工具。
- 复用预览令牌、任务取消、证据降级、严格输出和正式写入。
- 避免 Agent 对工具已生成的完整报告再次自由改写后保存。

### 阶段 D：主题与长期沉淀

- 由 DSH 承担主题连续对话。
- 保留主题归纳、差异展示和确认沉淀。
- 完成旧 `TopicSessionStore` 会话导入，再停止创建旧格式会话。

本阶段先拆成两个可独立验证的边界：

#### 阶段 D1：Agent 会话生命周期（已验收）

- 使用已发布的 `@deepseek-ai/dsh-session-persistence-jsonl`，把 DSH append-only 事件日志保存到知己数据根的 `agent/sessions/`。
- Agent 页通过 `session.list` / `session.snapshot` 读取重启后的会话，并在发送新消息时由 DSH `AgentRegistry.resume` 继续原事件历史。
- 数据目录迁移沿用现有递归复制；备份白名单和业务校验按 DSH `Session.fromRestore` 验证 JSONL，损坏会话拒绝导出/恢复而不静默清空。
- 本次不迁移 `TopicSessionStore`：当前 DSH 工具面尚未同时覆盖主题提案、差异展示和用户确认。先保留旧主题入口，避免为了“单轨”破坏每日分析、周/月复盘或主题确认闭环。

#### 阶段 D2：主题会话迁移（待真实证据）

- 只有在 DSH 工具能复用现有主题归纳与确认服务、并有真实使用证据证明连续 Agent 会话降低摩擦后，才导入旧 checkpoint、停止创建旧格式会话。
- 迁移必须先成功创建 DSH 会话并保留旧文件，再允许删除旧格式；不得静默丢失未经确认的主题提案。

### 阶段 E：收敛重复路径

- 根据已完成行为删除只服务旧临时会话或重复模型调用的代码。
- 更新桌面架构文档、Skill 兼容矩阵、备份类别和用户说明。
- 保留专业按钮入口；只有某入口已被证明重复且删除不增加使用摩擦时才移除。

## 10. 验收标准

- [ ] 当前日志、复盘、主题、项目、设置、备份与数据目录功能继续通过原有测试和人工主链路。
- [ ] 用户能在 Agent 页完成“读取本周材料 → 生成周复盘 → 打开正式结果”的连续任务。
- [ ] Agent 可组合至少两个不同领域能力完成任务，而不是只分类或跳转。
- [ ] 正式复盘仍经过现有 Schema、证据降级、预览确认和仓储写入，不由聊天自由文本替代。
- [ ] DSH Runtime 没有通用 Shell、终端、任意文件和任意 URL 能力。
- [ ] API Key 不进入 Renderer、Agent session、数据目录或备份。
- [ ] Agent turn、工具执行和现有复盘任务均可取消，失败不会留下半写入正式产物。
- [ ] 旧主题会话可导入并继续，已确认主题正文与索引不丢失。
- [x] Agent 会话随数据目录迁移，并能被备份校验与恢复（阶段 D1）。
- [ ] DSH 不可用时，现有专业页面和确定性工作流仍可继续使用。

## 11. 明确非目标

- 不把知己改造成能够编辑任意代码或文件的通用编码 Agent。
- 不采用 DSH Web UI 套壳替代当前 React 产品。
- 不让 Agent 自动修改个人核心画像、确认主题或删除数据。
- 不为 Agent 化引入云同步、多用户、向量数据库或后台常驻服务。
- 不在架构实施前顺手重写现有页面、仓储格式或全部 LangGraph 工作流。
