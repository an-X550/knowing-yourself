# 桌面端本地发布质量与设置页体验修复 Spec

## 1. 结论

本轮值得立即做，但它不是一次全局视觉重做，也不是 Agent、记忆或 MCP 架构升级。

真实问题是：已经分发给他人的 GitHub Release `v2.0.5` 暴露了核心日反馈失败、设置页信息堆叠、侧栏滚动归属错误和暗色下拉框破损；与此同时，本地开发运行的每日反馈能够成功，说明开发模式成功不能代表安装包可分发。本轮必须先修本地源码，再用全新生成的本地安装包完成同条件验收；GitHub 远程只在本地 Release Candidate 通过后进入第二阶段。

最小高性价比路径是：

1. 用同一服务商、模型、输入和全新用户数据对照开发模式、免安装包与安装包；
2. 重整设置页的信息架构和共享视觉规则，不全局换皮；
3. 补强 DeepSeek JSON Output 的失败识别、一次重试与安全退出；
4. 让每个版本产生独立、可追溯且经过安装验收的本地制品目录；
5. 本地通过后再只读核对旧 GitHub Release，并另发新修订版本，不覆盖 `v2.0.5`。

## 2. 当前证据

### 2.1 已知事实

| 事实 | 当前证据 | 用户影响 |
|---|---|---|
| GitHub Release `v2.0.5` 的用户遇到“AI 返回的日反馈格式无效” | 用户提供的安装版截图 | 日志→日反馈核心闭环被阻断 |
| 本地开发运行没有稳定复现同一错误 | 用户明确说明 | 不能把问题直接定性为通用业务逻辑错误 |
| 本地成功与用户失败是否使用同一服务商、模型、日志内容尚不明确 | 用户无法确认 | 必须先做同条件对照，不能把“打包差异”写成既定根因 |
| 当前日反馈请求已经发送 `response_format: { type: 'json_object' }` 并用 Zod 严格校验 | `openai-compatible-provider.ts`、`daily-runtime.ts` | 已有安全校验，但所有空内容、截断、非法 JSON 和字段错误都被压成同一句“格式无效” |
| 设置页同时承载外观、AI 服务、本地数据、个人背景、日志模板和版本更新 | `settings-page.tsx` | 页面过长、低频与高频任务争夺注意力 |
| “检查更新”不是版本检查 | 页面只是保存用户填写的 URL，再尝试 `window.open()` | 名称夸大能力，普通用户还被要求理解发布地址 |
| “检查更新”当前确实无法正常打开 | 保存后没有刷新 `appInfo`；`main.ts` 又拒绝所有新窗口 | 用户点击无结果，不是使用方法错误 |
| 暗色下拉框条纹来自 CSS 级联 | `.field select` 的 `background` 简写把 `background-repeat` 重置为 `repeat`，暗色规则随后重新设置箭头图片 | 所有使用该共享样式的暗色下拉框都可能出现重复箭头 |
| “数据留在本机”属于侧栏 DOM，但当前布局没有把侧栏与工作区滚动契约写成可验收行为 | `app-shell.tsx`、`index.css` | 用户看到状态卡随页面关系变化，无法形成稳定空间认知 |
| 当前本机免安装包程序为 `2.6.1`，但 `out/make` 仍保留 `zhiji-1.27.1-full.nupkg` | 2026-08-22 本地只读检查 | 固定路径下的 `Setup.exe` 可能是陈旧制品，存在误上传风险 |
| 标记根版本从 `2.0.4` 升到 `2.0.5` 的提交中，桌面端 `package.json` 仍为 `2.0.4` | 对提交 `5fa3266` 的本地 `git show` | 历史发布链存在根版本与 Electron 应用版本不同步的直接证据 |
| 仓库没有 GitHub Actions Release 工作流 | `.github/workflows/` 为空 | 构建、选择和上传制品依赖手工流程 |
| 当前打包 E2E 不执行真实每日反馈，也不覆盖暗色模式、设置页信息架构和侧栏滚动 | `e2e/desktop.spec.ts` | `npm run test:e2e` 通过不能证明这次用户事故不会发生 |

### 2.2 未验证假设

以下内容不得写成根因：

- GitHub “漏上传了部分 React 组件”；
- `v2.0.5` 的日反馈失败一定由 asar 缺依赖导致；
- 本地与用户使用了相同 DeepSeek 模型、相同 API 配置和相同日志输入；
- 当前 `2.6.1` 的新安装包仍会复现 `v2.0.5` 的全部问题；
- 用户说“UI 太丑”意味着需要全局改色、换框架或模仿苹果官网。

Electron Renderer 已被编译为整体 bundle。远端资产若传输损坏，通常表现为压缩包损坏、安装失败或应用无法加载；只坏某个控件更可能是旧制品、构建快照、CSS 或运行时行为问题。第二阶段仍需读取旧 Release 的资产和版本信息后再裁决。

## 3. 第一性原理与必要性判断

### 3.1 要解决的真实问题

用户需要的不是“更多组件”，而是一个可被他人安装、理解和完成核心任务的桌面产品：

```text
写日志
  -> 生成可信的每日反馈
  -> 明确知道数据在哪里、如何备份
  -> 在不同主题和窗口下仍能稳定操作
  -> 下载到的安装包与开发者验收的是同一份
```

### 3.2 为什么现在值得做

新功能必要性闸门不阻挡本轮，因为本轮是已有功能的 bug、兼容性、信息架构和发布质量修复：

1. 有当前、具体的用户截图和失败错误；
2. 日反馈直接服务项目最高频闭环；
3. 设置页和数据透明度直接影响非 CLI 用户能否安全使用；
4. 修复结果能通过同条件对照、普通测试、打包 E2E 和安装验收立即验证。

### 3.3 为什么不全局重做

“大圆角卡片很多、所有按钮同权、低频功能全部展开、开发者文案直接暴露”会产生明显的模板堆叠感。根因是信息层级和渐进展示不足，不是 React、Electron 或现有颜色无法承载产品。全局换框架会扩大回归面，却不能直接提高日反馈可靠性或制品一致性。

本轮保留现有浅色/深色、绿色强调色、React 组件和设计令牌；借鉴 Fluent 2 的空间关系原则，用接近程度表达分组、用留白表达层级，但不引入 Fluent UI、Tailwind、shadcn/ui 或另一套大型组件库。参考：[Fluent 2 Layout](https://fluent2.microsoft.design/layout)。

## 4. 目标与非目标

### 4.1 目标

- 让本地全新安装包完成日志→每日反馈闭环，并能从结构化输出异常中恢复；
- 让设置页从长页面卡片堆叠收敛为三个清晰任务域；
- 让普通用户理解存储、备份、恢复、API 配置和个人背景授权；
- 让侧栏和工作区具有稳定、独立的滚动关系；
- 修复所有受共享样式影响的暗色下拉框；
- 建立“验收哪一份、后续就上传哪一份”的本地 Release Candidate 流程；
- 详细记录 Pi、Hermes、Reasonix、MCP 和 DeepSeek 能力的采用与暂缓理由。

### 4.2 非目标

- 不全局换皮，不追求像素级模仿苹果官网；
- 不新增一级导航，不重写 Electron/React 架构；
- 不接入新的 UI 框架、Agent runtime、外部记忆 SaaS、向量数据库或 MCP；
- 不把每日反馈改成 Tool Call，不绕过 Zod 保存模型原始文本；
- 不实现自动更新、静默更新、更新服务器或代码签名；
- 不覆盖或替换 GitHub `v2.0.5` 的历史资产；
- 本轮文档阶段不修改产品代码、不打包、不操作 GitHub 远程；
- 不新增 hash、冻结 contract、截图 baseline 或独立质量 gate。

## 6. 设置页信息架构

### 6.1 页面骨架

设置继续保留一个一级导航入口，内部改成三个页内标签：

```text
设置

[通用] [AI 与个性化] [数据与隐私]

当前标签内容

知己 2.x.x
```

要求：

- 默认打开“通用”；
- 左下角“查看存储位置”直接打开“数据与隐私”；
- Agent 的“打开设置”恢复动作直接打开“AI 与个性化”；
- 切换标签不丢失同一页尚未提交的表单状态；
- 版本号是页面底部低权重文字，不再占独立卡片；
- 删除“发布地址（可选）”“保存地址”“检查更新”。

### 6.2 通用

只承载外观偏好：

- 跟随系统；
- 浅色；
- 深色。

使用紧凑的三段选择，不包裹成多层大卡片。当前主题继续即时生效并持久化；本轮不新增字体、动效或密度选项。

### 6.3 AI 与个性化

采用渐进展示：

```text
AI 服务
服务商        [DeepSeek ▾]
API Key       [••••••••••]
模型          deepseek-v4-flash
              [保存并测试]

高级设置 ▸
- 自定义 API 地址
- Agent 思考模式
- 仅保存、不测试
- 移除已保存的 Key

个人背景
未设置 / 已设置 · 未允许 AI 使用
[编辑个人背景]
```

规则：

- 服务商从三张大型卡片收敛为紧凑选择；
- 自定义 API 地址只在“其他兼容服务”下出现；
- DeepSeek 思考模式只在适用服务商下出现；
- 主路径只有一个主要操作“保存并测试”；
- 临时网络不可用但用户仍需保留配置时，可在高级设置选择“仅保存”；
- 移除 Key 保留确认对话框和危险样式；
- 个人背景默认只显示状态摘要，点击后展开编辑器；
- “允许 AI 使用”仍由用户显式选择，不因页面重排改变默认值或安全边界。

### 6.4 数据与隐私

拆成两个任务组：

```text
存储位置
D:\知己
可写入 · 23 个文件
[在资源管理器中查看] [更改位置]

备份与恢复
备份包含日志、复盘、项目、模板和 Agent 会话。
[创建备份] [从备份恢复]
```

规则：

- “在资源管理器中查看”是弱按钮或文字操作；
- “更改位置”在确认对话框说明会迁移现有数据并需重启；
- “创建备份”替代“导出可验证备份”；
- “从备份恢复”替代“选择备份并校验”；选择、校验、预览和确认属于恢复流程内部步骤；
- 成功/失败消息紧跟触发它的任务组，不插入另一个任务组；
- 恢复仍只允许写入空数据目录，不删除现有确认、校验或路径边界。

### 6.5 日志模板归属

日志模板管理完整移出设置页：

- 日志页“选择模板”附近增加“管理模板”；
- 进入后可新建、编辑、删除模板；
- 写日志时选择模板的既有能力不变；
- 模板仍存储在本地数据目录，不改变文件格式、备份和迁移行为；
- 删除模板仍需确认，已有日志不受影响。

## 7. 共享视觉与交互规则

### 7.1 产品气质

目标是“清晰、克制、完成度高的 Windows 本地优先工具”，而不是“苹果官网复刻”。保留现有颜色和整体气质，移除以下模板化表现：

- 每个功能都是一张巨大圆角卡；
- 所有按钮都使用绿色和相同视觉权重；
- 大量空白却没有表达任务分组；
- 开发者术语直接成为按钮文案；
- 状态提示按代码执行顺序随机插入布局。

### 7.2 层级与间距

- 使用既有 4px 网格，页面主要节奏收敛为 8/16/24px；
- 同一任务内部距离小于不同任务之间距离；
- 不依赖额外边框表达所有分组；
- 设置内容使用稳定的内容宽度，不让宽屏把字段和按钮拉得过散；
- 圆角继续复用现有令牌，但设置页避免大卡套大卡。

### 7.3 按钮权重

- 每个任务组最多一个绿色主按钮；
- 普通切换和次要操作使用中性按钮；
- “查看”“编辑”等轻量操作使用 ghost/文字按钮；
- 删除 Key、删除模板等不可逆操作保留危险样式和确认；
- loading、disabled、focus-visible 和键盘行为保持一致。

### 7.4 侧栏

侧栏固定为窗口高度，右侧工作区独立滚动：

```text
● 本地保存
  查看存储位置
```

- 删除当前大号 `privacy-card`；
- 不在侧栏展示完整本地路径；
- 点击“查看存储位置”打开“数据与隐私”；
- 窄窗口折叠侧栏时只保留状态图标和悬浮说明；
- 状态始终位于窗口左下角，不随右侧内容移动。

### 7.5 暗色下拉框

- 共享 select 样式必须显式保持 `background-repeat: no-repeat`；
- 避免后续 `background` 简写再次覆盖箭头的 repeat/position/size；
- 浅色、深色、disabled、hover 和 focus-visible 均需可读；
- 修复作用于全部共享下拉框，不只针对“关联项目（可选）”。

## 8. 每日反馈结构化输出

### 8.1 继续保留的边界

- 继续使用 DeepSeek/OpenAI 兼容的 JSON Output；
- 继续用 Zod 校验完整业务 Schema；
- 继续在校验通过后才原子保存正式反馈；
- 不把原始模型文本当正式反馈保存；
- 不把日反馈包装成虚假工具调用；
- 网络、鉴权、限流和模型不存在等错误不进入“格式重试”。

DeepSeek 官方要求在请求中设置 `response_format: { type: 'json_object' }`、在提示中明确 JSON 格式并合理设置 `max_tokens`；官方也明确提示 JSON Output 偶尔可能返回空内容。参考：[DeepSeek JSON Output](https://api-docs.deepseek.com/zh-cn/guides/json_mode/)。

### 8.2 失败分类

生产适配器至少区分：

- `empty_content`：没有正文；
- `truncated`：结束原因为长度或输出明显不完整；
- `invalid_json`：不是合法 JSON；
- `schema_mismatch`：JSON 合法但不符合日反馈 Schema。

诊断只保存在本地，允许记录：服务商、模型、失败类型、结束原因、输出字符数、Schema 问题摘要和时间。不得记录 API Key、Authorization header、日志正文、个人背景或完整模型原始输出。

### 8.3 一次自动重试

当且仅当首次失败属于上述结构化输出问题时：

1. 保留同一份经过边界控制的上下文；
2. 追加短修复指令，明确只返回符合既有 Schema 的 JSON；
3. 最多再请求一次；
4. 第二次成功则正常保存；
5. 第二次仍失败则安全退出，不保存残缺反馈。

不进行无限重试，不切换模型，不静默放宽 Schema，也不自动生成“看起来像反馈”的本地模板结果。

### 8.4 用户恢复入口

第二次失败时显示：

```text
AI 这次没有返回可用的反馈，你的日志和已有数据没有受到影响。
[重新生成] [查看诊断信息]
```

“查看诊断信息”只展示脱敏摘要；“重新生成”是一次新的用户操作。保留取消能力，取消不得触发自动重试。

## 9. 本地构建与 Release Candidate

### 9.1 本地成功的定义

本轮“本地版已修复”不等于 `npm start` 成功，而是：

1. 当前源码的普通测试、类型检查和 lint 通过；
2. 新生成的免安装包通过打包 E2E；
3. 新生成的 `Setup.exe` 在全新用户数据下完成安装；
4. 安装后的应用通过核心功能冒烟：启动、设置分区、日志/模板、本地保存入口、暗色 select、侧栏滚动和 Agent 新建会话；
5. 若存在安全可用的 DeepSeek 配置，再在安装包内完成一次脱敏日反馈冒烟；没有安全配置时必须明确记录“未验证”，不得索要 Key 或伪造通过。

### 9.2 版本独立制品

Electron Forge 的 Squirrel.Windows maker 会生成 `Setup.exe`、完整 `.nupkg` 和 `RELEASES` 三类制品，参考：[Electron Forge Squirrel.Windows](https://www.electronforge.io/config/makers/squirrel.windows)。

每次发布必须先确认目标输出目录，再生成并复制到版本独立目录：

```text
out/release-candidate/vX.Y.Z/
├─ Zhiji-Setup-vX.Y.Z.exe
├─ zhiji-X.Y.Z-full.nupkg
└─ RELEASES
```

要求：

- 根 `VERSION`、桌面 `package.json`、锁文件和安装后 `app.getVersion()` 一致；
- 清理操作只针对已解析确认的当前应用 `out/make/squirrel.windows/x64`，不得递归删除仓库根或用户目录；
- 记录对应 Git commit；
- 文件修改时间和 `.nupkg` 名称必须属于本次版本；
- 安装验收只使用版本目录中的 `Zhiji-Setup-vX.Y.Z.exe`；
- 后续 GitHub 只能上传同一份已经验收的文件，不临时重新打包；
- 当前失败由版本号、Git、明确目标目录和实际安装验收即可避免，不新增额外 hash 或发布门禁。

### 9.3 GitHub 第二阶段

本地验收完成后：

1. 只读检查 `v2.0.5` 的 tag、commit、资产名称、大小、版本元数据和发布时间；
2. 记录它与本地历史构建的差异，判断是旧制品、混版、构建缺依赖还是其他问题；
3. 不覆盖旧 Release；
4. 在用户再次明确确认后，为当时当前版本创建新的修订 Release；
5. Release Notes 说明设置页、侧栏、暗色下拉框、日反馈异常恢复和制品来源修复。

本 Spec 不授权 push、修改 Release、上传资产或删除远程内容。

## 10. 成熟方案评估

| [DeepSeek JSON Output](https://api-docs.deepseek.com/zh-cn/guides/json_mode/) | 保证合法 JSON 字符串，便于业务校验 | 采用并补强 | 直接对应日反馈；现有实现已接入，只缺空内容、截断、Schema 错误和重试处理 |
| Electron `shell.openExternal` | 在系统默认浏览器打开受信任 URL | 本轮不用于更新 | 官方能力可用，但当前没有值得保留的真实版本检查；删除死控件比把“开网页”包装成更新更诚实，参考 [Electron shell](https://www.electronjs.org/docs/latest/api/shell) |

## 11. 验收标准

### 11.1 设置与导航

- 设置页只有“通用”“AI 与个性化”“数据与隐私”三个页内标签；
- 日志模板不再出现在设置页，日志页可进入完整模板管理；
- “发布地址”“保存地址”“检查更新”不再对用户显示；
- 版本号以低权重文本显示且与安装包一致；
- AI 普通路径只显示服务商、Key、模型和“保存并测试”；高级项按需展开；
- 个人背景默认显示摘要，编辑和 AI 授权仍可完成；
- 存储位置、创建备份和从备份恢复按两个任务组展示；
- 原有数据迁移、备份校验、空目录恢复和危险操作确认没有退化。

### 11.2 侧栏与暗色模式

- 右侧工作区滚动时，侧栏和本地保存状态保持在窗口内；
- 完整数据路径不出现在窄侧栏；
- 浅色和深色的所有 select 只显示一个下拉箭头；
- 自动化行为测试覆盖导航、滚动、模板插入和关键控件可见性；
- 本轮不再扩展 900px/常用宽度/宽屏或 Windows 100%/125%/150% 的人工矩阵。

### 11.3 日反馈

- 同条件对照记录开发模式、免安装包和安装包结果；
- 正常 JSON 一次成功并保存；
- 首次空内容/截断/非法 JSON/Schema 错误时只自动重试一次；
- 首次失败、第二次成功时只保存一份正式反馈；
- 连续两次失败时不保存、不覆盖，并显示恢复入口；
- 鉴权、限流、网络和取消不被误判为结构错误重试；
- 诊断不包含日志正文、个人背景、API Key 或完整模型输出。

### 11.4 本地制品

- 普通测试、类型检查、lint、package、make 和打包 E2E 通过；
- 版本独立 RC 目录只包含本次版本的三个分发文件；
- 全新安装后的版本通过核心功能冒烟；
- 真实 DeepSeek 仅在存在安全可用配置时执行脱敏冒烟，否则明确记录未验证而不伪造通过；
- 未执行 GitHub 远程修改。

### 11.5 视觉验收边界

- 自动测试继续验证结构、文案、滚动、下拉框样式和键盘可访问行为；
- 本轮取消改前/改后截图、900px/常用宽度/宽屏截图、DPI 矩阵和像素比较；
- 不创建整页像素 baseline，不把主观“好看”变成新的 gate。

## 12. 风险与边界

| 风险 | 控制方式 |
|---|---|
| 设置页重排时丢失未保存表单 | 标签内容保持挂载或把草稿状态提升到设置页；测试切换标签后状态 |
| 移动模板入口导致用户找不到 | “选择模板”旁提供明确“管理模板”；保留原文件和仓储 |
| 一次重试增加费用和等待 | 只对结构化输出失败触发一次；页面阶段说明正在重试 |
| 严格 Schema 与模型偶发输出继续冲突 | 分类诊断并提供手动重试；不放宽正式数据契约 |
| 清理构建目录误伤其他文件 | 解析并核对绝对目标，只清理应用 `out/make/squirrel.windows/x64` |
| 删除更新 UI 后用户不知道去哪下载 | 本轮保持诚实边界；新 Release 通过发布说明分发，未来有真实需求再设计内置发布页 |
| UI 改完仍有人认为“丑” | 本轮不再追加视觉风格调整；只验证既有信息层级、按钮权重和行为边界，不承诺消除所有主观偏好 |
