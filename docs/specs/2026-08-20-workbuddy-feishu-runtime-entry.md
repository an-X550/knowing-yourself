# WorkBuddy 多通道运行入口：统一路由与受限写入

## 问题与目标

飞书智能体已能通过 WorkBuddy 访问本地“知己”项目，但现有消息没有稳定路由到项目的运行入口：它曾自行生成偏离日反馈契约的模板、只返回分析却未保存日志和反馈。根因是把只读分析器 `daily-analyzer` 当成了完整入口；实际持久化由 `log` skill 编排。该问题属于 WorkBuddy 的消息适配层，不属于飞书本身，因此同一规则也应适用于微信等上游通道。

目标是在不复制任何日/周/月分析模板的前提下，建立一个唯一的 WorkBuddy 消息适配层。该层将消息映射到既有 `.claude/` 权威定义，限制每个意图的读取、写入和确认边界，并在新结果通过本地复读验证后接回既有飞书与滴答分发能力。

## 第一性原理与范围

原始日志是高频、可追加的证据；日反馈是短周期的实验记录；`verified-patterns.md` 是有阈值的验证沉淀；核心画像、当前状态和主题认识是慢变量。不同证据寿命与误写代价要求不同写入权限，不能由单次飞书消息自动升级。

当前、具体的失败证据是：WorkBuddy 入口把“默认仅本地”写成永久策略，导致已经启用并在 Codex 中验证过的飞书文档沉淀和滴答任务创建从未进入调用链。最小修复不是新建服务，而是让入口在新结果验证成功后委托既有分发契约，并把平台相关调用收窄为可替换适配器。

本次创建 WorkBuddy 多通道运行入口、其可复制固定提示词和回归测试；复用既有分析模板、报告结构、来源白名单、幂等状态和确认门。它不新增服务器、数据库、队列、双向同步或通用外部写入能力，也不把 git、配置、部署、提交、代码开发能力暴露给任何消息通道。

## 架构

```text
WorkBuddy 任意消息通道
  -> 固定系统提示词（只进入本地项目并读取入口契约）
  -> .claude/workflows/workbuddy-message-entry.md
  -> 意图路由到既有 log / review / topic-thinking 等定义
  -> 本地持久化、复读校验
  -> 已启用配置授权时，按既有分发契约执行允许的外部副作用
  -> 原消息通道返回已验证结果或一条澄清问题
```

入口契约是唯一新增的运行真相；固定提示词只引用它，不重复路径、模板和业务规则。

## 路由与权限

| WorkBuddy 消息 | 权威运行定义 | 允许写入 | 禁止写入 |
|---|---|---|---|
| 未命中下列显式意图的单条日志 | `log.md` + 其引用契约 | 日志原文、当日反馈、满足验证契约的 `verified-patterns.md`、既有投递闭环必需的 `readiness_delivery_state` | 其他 `关于我`、周期报告、主题文件 |
| `周复盘` | 自然语言复盘路由中的周报定义 | `output.weekly_report` | 其他长期上下文 |
| `月复盘` | 自然语言复盘路由中的月报定义 | `output.monthly_report` | 其他长期上下文 |
| `项目复盘：<主题>` | 自然语言复盘路由中的项目定义 | `output.project_report` | 其他长期上下文 |
| `主题思考：<问题>` | `topic-thinking.md` | 无 | 所有主题文件及其他项目文件 |
| `确认沉淀：<主题>` | `topic-thinking-persistence.md` | 仅被确认主题与索引 | 无关主题、核心画像、周期报告 |
| `现在该补什么？` 等复盘时机问题 | `review.md` + `review-readiness-checker.md` | 无 | 所有项目文件 |
| 明确的年度复盘 / 人生设计 / 日志质量检查 | 对应现有 command 与 agent | 仅 `paths.md` 声明的对应报告 | 其他上下文文件 |

日记默认路由只适用于绑定“知己”工作区并安装固定提示词的 WorkBuddy 智能体。消息若不能满足既有 `log.md` 的日期与证据要求，入口只能追问一个会改变存档对象的问题，不能保存或分析。

所有成功写入必须按既有定义复读并通过最低结构校验；失败时只报告失败，禁止声称已保存。消息来源本身不构成分发授权；用户已经主动启用的 `output.result_distribution_config` 才是持续授权。新写入的允许来源验证成功后默认委托既有结果分发契约，用户本轮明确说“仅本地”则跳过两个外部渠道。来源白名单、配置开关、幂等与确认门不由本入口重复定义，飞书与滴答分别执行，一个失败不抑制另一个。

飞书适配器只读取被忽略的本地配置中既有 `lark_cli_path`，使用绝对路径调用官方 CLI，不依赖 PATH。滴答中国区由 WorkBuddy 自定义 MCP `https://mcp.dida365.com` 承担，只启用 `create_task` 并只接收共享契约允许的标题、截止时间和已绑定 `project_id`；缺少连接器时返回 `mcp_missing`，不得回退到 Codex 子进程。国际区使用对应的官方 TickTick MCP，不跨区猜测。

## 长期上下文保护

`context.core_profile` 与 `context.current` 永远不在 WorkBuddy 运行入口的直接写入白名单中。周/月/项目复盘只可在聊天结果末尾列出“拟议长期变更：结论、证据、目标文件”；未收到用户在直接本地会话中的明确确认前不得写入。

主题思考严格采用既有两阶段规则：首次讨论只读；确认沉淀时才读取持久化契约并写入。若 WorkBuddy 不能访问足以支撑确认的同一会话上下文，必须要求用户提供要确认的摘要，不能猜测或写入。

## 交付物与验证

1. 新增 `.claude/workflows/workbuddy-message-entry.md`，提供路由、读取顺序、白名单、默认分发、单次仅本地退出、渠道独立与失败语义；旧飞书入口只做兼容跳转。
2. 新增 `docs/workbuddy-agent-prompt.md`，提供任意 WorkBuddy 消息智能体可直接粘贴的固定提示词及最小连接器配置步骤；旧提示词只做兼容跳转。
3. 更新 `tests/workbuddy-feishu-entry-contract.tests.ps1`，静态验证入口、路由引用、写入边界、主题确认门、默认分发、仅本地退出、飞书绝对 CLI 路径和滴答 create-only MCP。
4. 更新项目入口事实、版本、状态和变更记录。

自动测试不能模拟 WorkBuddy、飞书或滴答账号侧写入，另保留一次人工验收：发送一份脱敏单日日志，确认原文与反馈均落到权威路径、飞书返回文档 URL/token、滴答只新增一项任务；重放同一消息必须零新增。再发送一份带“仅本地”的脱敏日志，确认本地仍写入而两个外部渠道均未调用。人工验收前可以完成代码交付，但状态保持“待首次真实人工验收”。
