## 路径 A：「深根」— Skill 极致化

### 定位

把当前的 Skill 打磨到"可以直接发给另一个 Claude Code 用户使用"的状态。

### 技术复杂度：⭐（极低）

零新代码。全部工作 = 提示词工程 + 文档 + 演示。

### 具体要做的事

| 阶段 | 任务 | 预估时间 |
|------|------|---------|
| 1. 验证闭环 | 跑通 ≥3 个"AI 发现→行为改变"的完整案例 | 2 周（取决于日志频率） |
| 2. 案例输出 | 把 3 个案例写成可传播的内容（博客/推文/视频） | 1 周 |
| 3. 新手引导 | 5 分钟上手流程：从"我是新用户"到"看到第一份分析" ≤ 5 分钟 | 3 天 |
| 4. 错误处理 | 日志格式不规范时的降级策略、空日志的友好提示 | 2 天 |
| 5. FAQ | 常见问题：隐私怎么保证？AI 分析靠谱吗？和传统日记 App 有什么不同？ | 1 天 |
| 6. 发布 | 发布到 GitHub Topics "claude-code-skill"、Reddit r/ClaudeCode、少数派等 | 1 天 |

### 评估矩阵

| 维度 | 评分 | 说明 |
|------|------|------|
| 技术复杂度 | ⭐ | Markdown + 提示词，零新语言 |
| 时间投入 | 2-4 周 | 课余时间可行 |
| 目标用户群 | 50-100 | Claude Code 用户 × 日记爱好者（小众交叉） |
| 商业模式 | 免费开源 | 通过博客/个人品牌间接变现 |
| 技术收获 | 中 | 提示词工程、开源运营、技术写作 |
| 核心风险 | 用户天花板低 | 依赖 Claude Code 平台，无法触达非程序员 |
| 第一性原理契合 | ⭐⭐⭐⭐⭐ | 完全践行"用优先于建" |

### 这一步做完的标志

- 有一个非你自己的人在 GitHub 上 ⭐ 了仓库
- 有 ≥1 条外部用户反馈说"这个分析让我发现了自己没注意到的模式"
- 你在"AI 日志分析"这个领域有了一篇有案例支撑的博客文章

## 路径 B：「出圈」— Bot/集成形态

### 定位

用户不需要安装 Claude Code，在他们已有的工具（飞书/Obsidian/微信）里写日志，自动收到 AI 分析。

### 技术复杂度：⭐⭐（中等）

需要一个后端服务：接收 webhook → 调 Claude API → 存储 → 推送结果。

### 推荐最小技术栈

```
用户写日志 ──→ Webhook ──→ Cloudflare Workers (免费额度: 10万次/天)
                                │
                                ├── Claude API (分析引擎)
                                │
                                ├── Cloudflare D1 (免费额度: 5GB 存储)
                                │
                                └── 推送回用户 (飞书消息 / Obsidian 通知)
```

### 为什么选 Cloudflare Workers 而不是传统服务器

- **免费额度慷慨**：个人项目基本不花钱
- **零运维**：不需要管理服务器、Docker、Nginx
- **技术栈现代**：Edge computing、TypeScript、Wrangler CLI——写进简历加分
- **渐进式**：以后可以平滑迁移到 Cloudflare Pages（全栈）

### 可选集成方向

| 平台 | 优势 | 技术要点 |
|------|------|---------|
| **飞书 Bot** | 大学生都用飞书；Bot API 成熟；消息卡片美观 | Webhook + 飞书开放平台 + 消息卡片 JSON |
| **Obsidian 插件** | 日记用户集中；插件生态活跃；可以上架社区市场 | Obsidian Plugin API (TypeScript) + 本地存储 |
| **Telegram Bot** | 最简单的接入方式；跨平台 | Telegram Bot API，1 天能跑通 MVP |
| **微信服务号** | 用户量最大 | 但审核严、接口受限，不推荐作为第一步 |

**推荐起步顺序**：Telegram Bot（1 天跑通验证功能）→ 飞书 Bot（触达你的目标用户群）→ Obsidian 插件（技术含量最高，简历加分最多）

### 具体要做的事

| 阶段 | 任务 | 预估时间 |
|------|------|---------|
| 1. 原型验证 | Telegram Bot：收到文本 → Claude API 分析 → 返回结果 | 3 天 |
| 2. 后端搭建 | Cloudflare Workers + D1 + 队列（异步分析） | 2 周 |
| 3. 飞书集成 | 飞书 Bot 申请 + Webhook 配置 + 消息卡片设计 | 1 周 |
| 4. 核心功能 | 日分析 + 周报 + 月报（复用现有 9 个视角） | 2 周 |
| 5. 成本优化 | 缓存常见分析模式、精简提示词降低 token 消耗 | 1 周 |
| 6. 测试打磨 | 内部测试 → 朋友试用 → 公开 50 人内测 | 2-4 周 |

### 用户故事

> 小王是某大学大三学生，每天用飞书写日志。某天他发现飞书工作台里有个"知己"Bot，点击开启后，每晚 10 点自动收到当天的日志分析。周日晚收到本周复盘，发现了一个他自己没注意到的模式：每次和室友吵架后的第二天，学习效率会暴跌 40%。他拿着这个数据去和室友认真谈了一次。

### 评估矩阵

| 维度 | 评分 | 说明 |
|------|------|------|
| 技术复杂度 | ⭐⭐ | 后端 + API + 部署，但 Serverless 大幅降低门槛 |
| 时间投入 | 6-12 周 | 课余时间约 1-2 个月 |
| 目标用户群 | 500-5000 | 飞书用户/日记爱好者，比纯 Claude Code 用户大 10-50 倍 |
| 商业模式 | Freemium | 免费：日分析 1 次/天；付费 ¥9.9/月：无限制 + 周报月报 |
| 技术收获 | ⭐⭐⭐⭐ | API 设计、Webhook、OAuth、Serverless 部署、TypeScript |
| 核心风险 | 平台依赖 | 飞书 API 变更；Claude API 成本需精算 |
| 第一性原理契合 | ⭐⭐⭐⭐ | 大幅降低使用摩擦（不需要安装 Claude Code），闭环速度不变 |

### 这一步做完的标志

## 路径 C：「独立」— 全栈 SaaS

### 定位

独立的 Web 应用，用户注册 → 写日志 → AI 分析 → 查看报告，不依赖任何第三方平台。

### 技术复杂度：⭐⭐⭐⭐（高）

完整的前后端 + 数据库 + 认证 + 支付 + 部署 + 运维。

### 技术栈建议

| 层 | 选择 | 选择理由 |
|------|------|---------|
| 前端 | React + TypeScript + Tailwind CSS | 生态最大、简历最通用 |
| 后端 | Node.js (Hono) 或 Go | Hono 与 Cloudflare 生态兼容；Go 性能好且对简历有差异化价值 |
| 数据库 | PostgreSQL (Supabase 托管) | 免费额度慷慨、自带 Auth |
| ORM | Prisma 或 Drizzle | TypeScript 生态主流 |
| 认证 | Supabase Auth 或 Clerk | 免费额度够用 |
| 支付 | Stripe 或 Lemonsqueezy | Lemonsqueezy 对国内开发者更友好 |
| 部署 | Vercel / Railway / Cloudflare Pages | 按需选择 |
| AI 引擎 | Claude API (Haiku 日常 + Sonnet 周月报) | 核心成本 |

### 用户故事

> 小李通过一篇博客文章发现了"知己"。她用 Google 账号一键登录，写了第一篇日志。5 分钟后收到了一份 AI 分析："你今天的日志里有 3 个高频词——焦虑、秋招、简历。但你过去 7 天的行为数据显示，你花在投简历上的时间不到总学习时间的 5%。实际最焦虑的事和实际花时间的事不在一个方向上。建议明天分配 1 小时专注处理简历相关事务。" 小李把这个洞察截图发了朋友圈。

### 评估矩阵

| 维度 | 评分 | 说明 |
|------|------|------|
| 技术复杂度 | ⭐⭐⭐⭐ | 全套技术栈，独立运维 |
| 时间投入 | 6-12 月 | 与考公/实习的时间冲突风险高 |
| 目标用户群 | 10,000+ | 任何写日记的人（不限于程序员） |
| 商业模式 | SaaS 订阅 | ¥19-39/月，或按分析次数付费 |
| 技术收获 | ⭐⭐⭐⭐⭐ | 完整产品开发经验，简历含金量最高 |
| 核心风险 | **时间黑洞** | 核心假设未被验证，大量时间花在非核心功能上 |
| 第一性原理契合 | ⭐⭐ | 当前阶段焦点是"用"而非"建"——需要先验证核心假设 |

### ⚠️ 暂不启动此路径的理由

[docs/first-principles.md](docs/first-principles.md) 明确规定：

> "先验证核心价值。至少有一条 AI 洞察导致了一个可验证的行为改变。"

全栈 SaaS 是这个原则的完美反例。你会把大量时间花在：
- 注册登录系统（与核心价值无关）
- UI 框架选型和打磨（在没有人用之前无法判断什么 UI 是对的）
- 支付集成（在有用户愿意付费之前是纯成本）

**启动 C 的前提条件**：
- [ ] 路径 B 有 ≥200 活跃用户且 ≥10% 付费转化率
- [ ] 路径 B 的用户强烈要求 Web 版（"我想在浏览器里看报告"）
- [ ] 考公/实习已稳定，有持续的空闲时间

## 不推荐的形态（及原因）

| 形态 | 为什么不推荐 |
|------|------------|
| **移动 App (iOS/Android)** | 日记输入体验在手机上不如电脑；开发和维护成本极高（两套代码或 React Native）；审核周期长；用户获取成本高。除非 B/C 跑通后有强需求，否则跳过 |
| **Chrome 扩展** | 场景不匹配——日记是主动输入行为，浏览器扩展更适合被动抓取（网页标注、浏览记录分析） |
| **微信小程序** | 用户群匹配但审核严格（涉及 AI 生成内容需要备案），且小程序生态封闭，数据可迁移性差 |
| **本地桌面应用 (Electron)** | 和 Claude Code Skill 一样限于单机，但需要维护一个 Electron 壳——徒增复杂度而不扩大用户群 |
