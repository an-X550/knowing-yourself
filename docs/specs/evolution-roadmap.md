# 产品进化路线图

> 这是一份兼具对外展示与内部决策的路线图。它首先回答“为什么现在这样做”，再展开“以后可能做什么”。

**前置阅读**：[第一性原理行动指南](../first-principles.md)  
任何进化路径都以“先验证闭环，再扩形态”为前提。

---

## 战略摘要

**知己** 当前最适合走的路线，不是立刻做更重的产品形态，而是先把现有 Skill 打磨到能稳定产出“AI 发现用户原本不会发现的洞察，并推动一个可验证的行为改变”。

这意味着当前主路线仍然是 **路径 A：本地复盘闭环极致化**。

飞书沉淀与滴答提醒已经作为可选结果出口落地；Windows 桌面客户端也已作为面向非 CLI 用户的本地优先入口完成 MVP。两者都没有改变本地文件权威，也不等于核心行为闭环已经获得外部用户验证。路径 B 的入口工程已部分落地，下一阶段仍须以真实使用证据决定是否继续扩展。
路径 C（独立 Web SaaS）也不是永远不做，而是明确放到“B 跑通后再评估”。

对潜在协作者或面试官来说，这份路线图想表达的核心不是“我未来有很多想法”，而是“我知道当前最该做什么，也知道现在不该做什么”。

## 当前基点

| 指标 | 当前情况 |
|------|---------|
| 当前形态 | Codex 自然语言入口 + Claude 命令兼容 + Electron Windows 客户端；本地 Markdown 为权威 |
| 核心资产 | 日反馈、周期复盘、主题思考、人生设计、用户分发包与质量回归 |
| 当前用户形态 | 单人长期自用；外部用户试用待验证 |
| 已有证据 | 运行契约回归、用户版边界测试、飞书历史同步与滴答创建冒烟 |
| 当前缺口 | 代表性行为改变案例、外部用户反馈、真实通知与新写入持续验证 |
| 当前版本 | v1.27.9 |
| 当前主要风险 | 把“外部写入成功”误当成“核心行为闭环已验证” |

### 这个基点意味着什么

1. 项目最强的部分已经不是“能不能分析”，而是“是否能稳定产出值得行动的洞察”。
2. 项目当前最弱的部分也不是“缺 Web、缺 Bot、缺数据库”，而是“缺足够强的闭环证据”。
3. 因此，路线判断不应围绕“做什么形态更酷”，而应围绕“哪条路径最能加快验证核心价值”。

## 当前判断：为什么现在优先路径 A

### 结论

现阶段最优选择是继续走 **路径 A：Skill 极致化**，优先验证闭环、补案例、降上手摩擦，而不是提前转向 Bot 或 SaaS。

### 理由 1：核心假设还没被证明到足够强

项目的第一性原理已经写得很清楚：  
**至少有一条 AI 洞察导致了一个可验证的行为改变。**

当前项目已经有：

- 多视角分析能力
- 月度综合能力
- 真实长期日志数据

但还缺：

- 足够清晰的“洞察 -> 行动 -> 验证结果”闭环案例
- 来自非作者本人的使用反馈
- 对外能说明项目价值的代表性样本

在这个阶段直接进入路径 B 或 C，会把大量时间花在技术壳层，而不是价值验证本身。

### 理由 2：路径 A 最符合当前资源约束

当前项目的资源现实是：

- 用户规模极小
- 作者时间宝贵
- 项目已经有一套可工作的分析骨架

在这种情况下，最优动作不是再搭一层基础设施，而是把现有能力做得更“可复用、可传播、可解释、可验证”。

### 理由 3：路径 A 对外展示价值并不低

对协作者或面试官来说，真正有说服力的不是“我会做一个 Bot”或“我能写一个 Web 应用”，而是：

- 我能从真实问题出发收缩范围
- 我知道哪些能力已经够用了
- 我能先证明价值，再决定是否扩形态

这种判断力本身，就是这份路线图最重要的展示内容。

## 升级门槛：何时进入 B，何时再评估 C

## 从 A 进入 B 的门槛

当以下条件大体满足时，进入路径 B 才是顺势而为，而不是“想做点更大的东西”：

- [ ] 跑出至少 3 个“AI 发现 -> 行动改变 -> 后续验证”的完整案例
- [ ] 至少有 1 位非作者用户明确反馈“这套分析让我发现了自己之前没看到的模式”
- [ ] 已经能用一篇文章、一个 README 段落或一个 demo 清楚讲明项目价值
- [ ] 当前痛点开始从“分析值不值”转为“现有本地 AI 入口仍明显限制真实试用与持续使用”

### 不该进入 B 的信号

- 还在用想象中的用户需求替代真实反馈
- 还没有形成代表性案例就想先做分发
- 主要动力是“想补技术栈”而不是“现有入口已经限制验证速度”

## 从 B 评估 C 的门槛

只有当路径 B 已经证明“更低摩擦的入口确实带来了稳定价值”时，路径 C 才值得进入评估。

建议门槛：

- [ ] 路径 B 已经有稳定活跃用户，而不是一次性试用
- [ ] 已经出现明确的 Web 诉求，例如需要浏览器内查看报告、管理历史记录、跨设备访问
- [ ] 已经验证用户愿意为持续分析体验付出成本或迁移成本
- [ ] 作者有足够持续时间投入，而不会让 SaaS 变成新的时间黑洞

### 当前为什么不做 C

路径 C 会显著增加：

- 认证与权限系统
- 数据存储与访问层
- 前端体验设计与维护
- 部署、监控、支付等外围复杂度

这些都不是当前最稀缺的能力。当前最稀缺的，是 **强闭环证据**。

## 近 12 周动作

这部分不是完整项目计划，而是当前阶段最值得推进的动作清单。

| 阶段 | 目标 | 产出 |
|------|------|------|
| 第 1 阶段 | 补闭环证据 | 3 个可复述的“洞察 -> 行动 -> 验证”案例 |
| 第 2 阶段 | 补对外表达 | 1 篇能讲清楚项目判断与案例的文章或说明 |
| 第 3 阶段 | 降上手摩擦 | 1 份更清晰的新手入口说明 / 试用路径 |
| 第 4 阶段 | 小范围外部验证 | 至少 1 位非作者用户试用反馈 |
| 第 5 阶段 | 再判断是否进 B | 基于证据，而不是基于冲动，重看路线图 |

### 当前最值得投入的事项

1. 把“分析很有意思”变成“分析真的改变了行为”。
2. 把“我自己知道它为什么有价值”变成“别人也能快速理解它为什么有价值”。
3. 把“技术路线图”写成“有门槛的阶段决策”，而不是开放式愿望清单。

## 附录：路径 A / B / C 展开

## 路径 A：Skill 极致化

### 定位

把当前系统打磨到“可以直接发给另一个 Codex 或 Claude 用户试用，并且对方能较快看到价值”的状态。

### 核心任务

| 方向 | 说明 |
|------|------|
| 闭环案例 | 跑出可验证行为改变，而不是只积累漂亮分析文本 |
| 新手引导 | 降低第一次使用成本，让试用路径更短 |
| FAQ 与边界说明 | 解释隐私、可靠性、适用场景与不适用场景 |
| 对外表达 | 用案例而不是抽象口号描述价值 |

### 这条路径的价值

- 最符合当前第一性原理
- 几乎不新增技术壳层
- 能最快检验“项目值不值得继续做大”
- 对协作者 / 面试官同样有展示价值，因为它体现了明确的产品判断

### 这条路径做完的标志

- 有代表性的闭环案例
- 有至少一位外部用户的有效反馈
- 有能对外复用的表达材料

---

## 路径 B：Bot / 集成形态

### 定位

当“价值已被证明，但现有本地 AI 入口仍太窄”成为主要矛盾时，再把项目扩成独立 Bot 或其他更低摩擦的入口形态。现有飞书沉淀与滴答提醒只是结果出口，不作为进入 B 的证据。

### 候选方向

| 方向 | 价值 | 风险 |
|------|------|------|
| 飞书 Bot | 更贴近目标人群，适合结构化消息输出 | 平台依赖较强 |
| Telegram Bot | 原型最快，验证入口摩擦最小 | 与目标场景契合度一般 |
| Obsidian 插件 | 更贴近日记生态，也更适合展示技术深度 | 插件维护成本更高 |

### 适合进入 B 的前提

- A 已证明核心价值
- 新问题变成“如何让更多人更低摩擦地用”
- 技术投入是为解决真实瓶颈，而不是为了补形态

### 这条路径的意义

如果 B 跑通，它会同时验证两件事：

1. 项目价值是否能跨出“作者本人 + 本地 AI 工具”语境
2. 更完整的工程化能力是否值得继续下注

---

## 路径 C：独立 Web SaaS

### 定位

只有在 B 已经证明更广入口和更轻体验确实带来稳定价值后，才考虑进入独立 Web 应用阶段。

### 这条路径会带来的能力

- 完整前后端产品经验
- 更强的数据留存与多端访问能力
- 更清晰的商业化承载空间

### 这条路径当前不该启动的原因

- 它最重
- 它最容易分散注意力
- 它对当前最关键的问题帮助最小

换句话说，C 不是错误方向，但它是 **当前阶段的错误顺序**。

| 形态 | 当前不推荐的原因 |
|------|----------------|
| 移动 App | 开发与维护成本高，当前价值验证不足以支撑 |
| 微信小程序 | 审核与生态约束重，容易提前陷入平台问题 |
| Chrome 扩展 | 与“主动写日志 -> 复盘分析”的场景不匹配 |
