# 知己桌面端与 DSH 插件平台融合执行计划

## 1. 计划目标

在不把知己改造成通用 Agent 平台的前提下，验证能否将现有固定工具注册方式升级为基于 DeepSeek Harness（DSH）原生 Profile、Bundle、Loader 和 inventory 的插件运行方式；验证通过后，再逐步提供已核验扩展的启用、停用、安装、更新和移除能力。

最终产品仍然回答一个明确问题：**怎样帮助用户更低摩擦地完成记录、反馈、周期复盘和行动验证？** 插件是扩展该闭环的手段，不是新的产品中心。

本计划保留 P0-P4 的阶段结构，但当前只批准执行 P0。公共插件市场、任意 Renderer UI、不可信代码沙箱和通用电脑操作不进入当前执行范围。

## 2. 执行原则

1. **复用上游，不复制机制**：DSH 已有 Loader、Profile/Bundle、HMR、inventory 和 CLI 包管理时，知己只做宿主适配；发布包未暴露或版本不匹配时暂停，而不是复制源码实现。
2. **领域边界先于能力数量**：默认插件只扩展复盘相关工具、Skill、提示词段和设置，不引入 Shell、代码编辑或任意文件访问。
3. **权限由知己 Main Process 持有**：知己不向插件上下文提供 API Key、业务仓库对象或 Renderer 能力，正式写入继续经过现有预览和确认语义。DSH 插件本身是 Node 宿主代码，仍可能自行访问 OS 用户可读资源，因此本原则不是安全沙箱。
4. **先证明兼容，再改主链路**：P0 未证明发布包和 Electron Utility Process 可用前，不重构当前稳定运行时。
5. **一个阶段一个可验证结果**：执行模型不得同时铺开多个阶段，也不得用占位实现宣称完成。
6. **不追求错误的零重启**：配置可热更新；插件 Bundle 变化按官方要求重启 Agent Utility Process；整个桌面端保持运行。用户文案使用“重新加载扩展”，不使用“零重启热插拔”。
7. **不新增无事故依据的门禁**：依赖版本、锁文件、类型和测试足够时，不增加自定义 hash、冻结 contract 或重复 baseline。

## 3. 模型协作方式

### 3.1 sol 模型职责

sol 用于每个阶段开始前的规划与复核，不直接并行规划所有后续实现。它应当：

- 阅读本文、目标架构、当前源码和上一阶段交付记录；
- 核验上游 DSH 当前锁定版本的真实 API，不根据概念文档猜接口；
- 把当前阶段细化为文件级变更、测试和回退点；
- 标出未知项及验证方式，但不借机改写已确认的产品定位；
- 若发现架构假设不成立，先更新决策记录并停止进入下一阶段。

### 3.2 执行模型职责

其他模型一次只执行一个已细化阶段：

- 开始前检查工作树，避免覆盖用户已有改动；
- 优先修改现有模块，不创建平行的第二套运行时或插件协议；
- 完成实现、自动化测试和必要文档；
- 明确报告实际验证结果、未完成项和下一阶段输入；
- 不自行扩大到市场、沙箱、任意 UI 或通用 Agent 能力。

### 3.3 每阶段交接格式

每个阶段结束时，执行模型必须留下以下内容：

1. 本阶段解决的具体问题。
2. 实际改动文件与关键设计决定。
3. 执行过的测试及结果。
4. 仍存在的风险和已知限制。
5. 回退方式。
6. 下一阶段可以依赖的稳定事实。

## 4. 开始实施前的工作区要求

当前工作区已有与凭据存储、版本和既有 DSH 文档相关的未提交改动。正式执行前应先由用户处理或提交这些改动，再从干净、可回退的分支开始。不得把本计划的实现混入来源不明的工作树变更。

实施模型应按顺序阅读：

1. `AGENTS.md`。
2. `.claude/shared/ai-operating-principles.md`。
3. `PROJECT_STATUS.md` 与 `CHANGELOG.md` 最近 5 条。
4. `docs/specs/2026-08-20-dsh-plugin-platform-architecture.md`。
5. `docs/specs/2026-08-20-deepseek-harness-agent-architecture.md`。
6. `apps/zhiji-desktop/docs/architecture.md`。
7. `apps/zhiji-desktop/docs/dsh-integration-notes.md`。
8. 当前 DSH runtime、IPC、preload、设置页、测试与锁文件。
9. `D:\AI\deepseek-harness` 中和当前阶段直接相关的源码。

修改项目文件时同时遵守 `docs/development-governance.md`。上游源码只用于核验和构建，不复制到知己仓库。

### 4.1 2026-08-21 已核验基线

- 知己使用的 DSH 核心包为 `0.1.0-rc.8`，但官方 npm 上 `@deepseek-ai/dsh`、`dsh-app-boot` 和 `dsh-host-plugin-inventory` 的最新发布版本分别为 rc.7、rc.6 和 `0.0.1-rc.3`。P0 必须解决版本闭合，不能混装后直接实施。
- 官方 `dsh plugin` 已实现 add/remove/update，但只是 pnpm 薄封装和 Bundle list reconcile；它不是插件商店，也没有签名、审核或事务式回退。
- 官方文档明确要求 Bundle 增删更新后重启运行中的 Profile；Profile/home patch 配置修改才会热更新。
- 官方 inventory 是只读快照，只给出 entry id、module specifier、effective enablement 和 Fiber phase；版本、来源、兼容性和写操作不属于它。
- 官方发现入口是 GitHub `dsh-plugin` topic。社区目录和社区 marketplace 可以作为调研样本，不作为知己依赖或安全背书。
- 上游实测：官方 CLI E2E 的本地 Bundle 安装/移除和更新 reconcile 用例通过；Profile patch 的 transactional HMR 单测通过；inventory 单测通过。Windows Profile 生命周期 E2E 在清理临时目录时出现 `EPERM`，说明打包和进程回收仍需在 P0 单独验证。

## 5. P0：上游兼容性与集成路径验证

### 5.1 要解决的问题

在主运行时重构前，证明知己锁定的 DSH 发布版本确实能提供所需插件基础设施，并确认 Electron Utility Process 中的最小启动、重启和打包路径。

### 5.2 工作项

- 从知己锁文件和已下载源码确认实际 DSH/Cordis 版本、导出入口和 peer dependency。
- 核验以下能力能否从相互兼容的发布包直接消费：app-boot、Loader、Profile/Bundle、HMR 和 plugin inventory。
- 在测试或临时目录建立最小 Profile：只加载一个无副作用的只读测试插件。
- 验证插件能被发现、加载、调用、停用，并能在 Utility Process 重启后恢复。
- 验证 Profile 配置变化是否可由上游机制热更新。
- 包管理默认只评估调用 DSH 官方 `dsh plugin` CLI。当前 CLI 的 `plugin.ts` 不是公开库入口；除非 P0 找到版本匹配且官方导出的库 API，不得 deep import 或复制其内部实现。
- 核验 Electron 打包版如何提供 pnpm。官方 CLI 要求 pnpm 位于 PATH，普通用户机器不能被假设已安装；优先评估随应用提供受控 CLI/包管理运行时，其次才是限制为预构建 npm/tarball。
- 记录 SDK client 对取消、通知和双向请求的现有限制；在其未达到当前 MessagePort 能力前，不替换现有桥。
- 验证开发环境和打包应用中依赖解析、资源路径与子进程/Utility Process 启动方式。

### 5.3 交付物

- 一份 P0 决策记录，包含实测 API、最小调用示例、打包结果和选定的包管理路径。
- 一个仅用于自动化验证的最小插件 fixture；不得成为第二套插件规范。
- 对目标架构文档中已证实或被推翻的假设进行同步修订。

### 5.4 验收标准

- 测试插件可通过 DSH 原生 Profile/Bundle 加载，而不是被知己手工 import。
- inventory 能返回官方承诺的 entry id、module specifier、effective enablement 和 Fiber phase；版本和来源可从 Profile manifest/lockfile一致地补充。
- Profile patch 启停/配置变化可在不重启 Electron 的情况下生效；Bundle 增删更新可通过重启 Utility Process 生效。
- 打包环境至少完成一次离线 smoke test。
- 如果发布包缺少必要导出，明确选择“固定官方构建产物”或“等待/推动上游发布”；不得默默复制 Loader 源码。

### 5.5 停止条件

出现以下任一情况时，P0 结束后暂停实施并重新裁决：

- DSH 发布包无法合法、稳定地消费 Loader/Profile 能力；
- 必需包只能通过不受支持的 deep import、复制上游源码或混用不兼容 rc 版本才能工作；
- Utility Process 中的启动或打包必须大幅 fork 上游；
- 包管理只有重写依赖解析器才能工作；
- 基础接入会破坏当前取消、确认或数据边界，且没有局部兼容方案。

## 6. P1：将现有 Runtime 演进为知己 Profile Host

### 6.1 要解决的问题

当前工具由知己静态注册，无法使用 DSH 的组合和插件生命周期。P1 只替换组合方式，不改变用户功能和前端交互。

### 6.2 工作项

- 在 Utility Process 内使用 P0 选定的 DSH 官方启动和加载入口。
- 建立知己默认 Profile 与内置 Bundle。
- 把现有工具注册、system prompt、会话与模型适配整理为内置 `zhiji-base` Host 插件或等价 Bundle 成员。
- 保留 Main Process 的模型 relay、领域服务和正式写入权限。
- 保留现有 MessagePort 协议、流式事件、取消、审批和 JSONL 会话恢复行为。
- 将静态 `TOOL_DEFINITIONS` 的职责迁移到插件注册；不得同时维护两份工具真相。
- 对 Profile 启动失败提供明确错误和安全回退：Agent 不可用时，日志、复盘等非 Agent 页面仍可使用。

### 6.3 验收标准

- 现有 Agent 行为回归测试全部通过。
- 默认 Profile 中的现有工具均来自 DSH 插件注册和 inventory。
- 取消、确认、恢复和异常退出行为不弱于改造前。
- 无插件管理 UI 也能以默认 Profile 正常启动，普通用户无额外配置成本。
- 删除旧静态注册路径后不存在双重注册或工具名冲突。

## 7. P2A：插件身份、能力与权限契约

### 7.1 要解决的问题

DSH 插件代码属于宿主代码。若不定义知己侧能力边界，开放插件会直接扩大个人数据和正式写入风险。

### 7.2 工作项

- 以 DSH manifest/Loader entry id 为加载真相；版本和来源读取 Profile manifest/lockfile。只有知己领域 API 需要时，才增加最小兼容元数据：显示名、说明、已验证 DSH/知己版本、领域能力声明和可选设置 schema。
- 能力声明只描述插件希望调用的知己宿主能力，不创造另一套插件生命周期。
- Main Process 按插件身份分发知己领域能力，默认拒绝未声明或未授权的知己 API。
- 首批能力分为：只读日志/复盘、只读项目、联网读取、生成预览、提交正式写入、界面导航。
- 继续让写入型操作经过预览与用户确认；插件不得绕开领域服务直接修改业务文件。
- API Key 只在 Main Process 使用，不传入插件上下文、Renderer 或会话文件；同时明确这无法阻止插件自行读取其他 OS 可访问资源或联网。
- 会话恢复时记录必要的插件 identity/version；插件缺失时给出可理解的降级信息，不伪造原工具结果。

### 7.3 验收标准

- 未声明能力的插件调用被 Main Process 拒绝，并能定位到插件身份。
- 只读插件无法通过知己能力桥获取写入能力、API Key 或业务文件句柄；不宣称限制其自身 Node/OS 权限。
- 写入插件仍触发既有预览和确认流程。
- 缺失、禁用或版本不兼容插件不会导致整个桌面应用无法启动。
- 元数据没有复制 DSH manifest 已经提供的字段和校验逻辑。

## 8. P2B：插件 inventory、启停与 Agent Runtime 生命周期

### 8.1 要解决的问题

普通用户需要在知己内部看见和控制扩展，而不需要理解 `cordis.yml`、CLI 或本地开发服务器。

### 8.2 工作项

- 在 Main Process 增加薄插件管理服务：Loader 状态读取 DSH inventory，包版本和来源读取 Profile manifest/lockfile，已验证兼容性读取知己最小元数据。三者职责不得混淆。
- 增加共享 IPC schema、Main handler 和 preload API；Renderer 不直接操作 Profile 文件。
- 设置页新增“复盘扩展”区域，展示可证明的名称、版本、来源、能力、状态、错误和兼容性；无法证明时显示“未知/未验证”，不能从 inventory 猜测。
- 支持启用、停用与配置编辑。
- 配置变化优先使用 DSH 原生热更新；Bundle 成员变化由 Main Process 安全重启 Utility Process。
- Agent 正在生成或等待用户确认时，不强制杀进程；先提示等待、取消当前会话，或在空闲后应用变更。
- Runtime 重启不关闭桌面端，不影响日志、项目和已有正式产物。
- 重启失败时恢复上一份可启动 Profile，并在设置页呈现错误。

### 8.3 验收标准

- 用户可在设置页完成插件查看、启用、停用和配置，无需命令行。
- 配置更新无需重启整个桌面端；Bundle 变化最多重启 Agent Utility Process。
- 进行中会话不会因后台插件操作静默丢失。
- 一个插件启动失败不会拖垮非 Agent 功能。
- UI 使用“复盘扩展”等产品语言，不把知己首页改造成开发者控制台。

## 9. P3：可信插件安装、更新与移除

### 9.1 要解决的问题

高级用户需要接入已核验的 DSH Bundle，而不仅能切换预装插件；同时不能为此自建市场和包管理内核。普通用户的一键社区市场安装不属于 P3。

### 9.2 初始支持范围

- 来源：优先预构建且固定版本的 npm 包或 tarball；本地包用于开发。GitHub source 安装只有在固定 commit、作者提供独立 `prepare`、用户明确允许构建脚本且 P0 验证通过时才开放。
- 信任：只安装知己内置、官方或人工核验并由用户明确选择的插件；安装前说明插件代码将以 Node 宿主权限运行。
- 平台：不建设账号、上传、审核、搜索排名或远程下架后台。
- UI：第一版只提供明确包规格输入/选择、来源与 Bundle patch 预览、风险确认、进度和错误恢复；不内嵌 GitHub topic 浏览器，不把社区收录标记成安全认证。

### 9.3 工作项

- 调用版本固定的官方 `dsh plugin` CLI 执行安装、更新和移除；若 P0 证明官方公开库入口更稳定，可用公开库入口替代，但不得使用内部 deep import。
- 依赖仍由 package version、lockfile 和包管理器维护，不增加自定义内容 hash。
- 在临时 Profile 中安装、dump config 并启动 smoke；只有成功后才切换当前 Profile。smoke 只证明可加载，不代表安全审核。
- 失败时保留上一份可启动 Profile 和已安装版本，显示包管理器原始错误的安全摘要。
- Bundle 切换后只重启 Utility Process。
- 卸载前检查当前启用状态和会话依赖；不删除业务数据或历史正式产物。
- 为测试提供本地 fixture，CI 和打包 E2E 不依赖公开网络。

临时 Profile 启动 smoke 是本计划唯一新增的发布前切换保护。它防止的具体事故是：运行期安装的第三方依赖在用户机器上解析或启动失败，若直接覆盖当前 Profile，会让 Agent 下次启动整体不可用。Git、版本号、类型和仓库内测试无法覆盖用户运行时刚安装的外部包，因此这里需要先启动后切换；无需再叠加自定义 hash 或永久双写。

### 9.4 验收标准

- 可从至少一种预构建远程来源和一种本地来源安装固定版本的兼容 fixture。
- 安装、更新、移除均通过 DSH 官方 Profile/Bundle 机制完成。
- 失败安装不会破坏当前可用 Agent Runtime。
- 更新后 inventory 显示新的 Loader 状态，Profile manifest/lockfile 显示新版本，会话新调用使用新版本。
- 移除插件不会删除用户日志、复盘、项目和历史会话。
- 打包版完成安装失败回退和成功切换 E2E。

## 10. P4：插件作者体验与示例

P4 不包含任意 Renderer UI。插件身份与权限契约作为 P2A 先完成，inventory、启停和 Runtime 生命周期作为 P2B 接续实施；两者共同构成架构文档中的 P2。

### 10.1 工作项

- 提供一个最小“复盘视角”示例插件：读取已授权复盘数据，注册一个工具或 Skill，返回结构化洞察，不进行正式写入。
- 提供 manifest/兼容元数据说明、开发命令、测试、打包和本地安装步骤。
- 明确推荐作者使用 DSH Web UI 和原生 HMR 做开发调试；知己只负责最终安装与产品化运行。
- 给出兼容性、能力申请、设置 schema、错误处理和版本升级约定。
- 说明禁止依赖知己私有内部路径，插件只能使用稳定宿主能力和 DSH 公共接口。

### 10.2 验收标准

- 一个不了解知己内部源码的开发者可按文档创建、调试、打包并本地安装示例插件。
- 示例插件在 DSH 开发环境和知己打包版中均可运行。
- 示例没有引入第二套插件 API，也没有要求复制知己仓库代码。

## 11. 暂缓范围及重新评估条件

### 11.1 任意插件 Renderer UI

暂不允许插件向知己 React 应用注入页面、组件和样式。只有出现至少两个无法由工具、Skill、设置 schema 或通用结果卡片表达的真实插件需求，且这些需求直接服务复盘闭环时，才单独立项。

### 11.2 公共插件市场

暂不建设上传、搜索、排行、审核、签名、撤回和账号系统。官方目前只有 GitHub `dsh-plugin` topic 作为发现入口；社区目录/marketplace 缺少官方背书和统一审核，暂不直接集成。只有经过一段时间的兼容插件清单积累，且发现问题成为真实阻碍时再评估。

### 11.3 不可信代码沙箱

当前只支持用户明确选择的可信插件。若未来允许一键安装陌生作者代码，必须单独设计进程隔离、文件/网络权限、供应链审查和紧急撤回；不能把模型工具确认误当作插件代码沙箱。

### 11.4 通用 Agent 能力

Shell、任意文件编辑、代码仓库操作、浏览器自动化和跨应用控制不作为默认能力。单个能力只有在能说明它如何改善复盘闭环、为何现有领域工具不足、以及如何立即验证时，才经过新功能必要性闸门另行评估。

## 12. 测试矩阵

每阶段按风险选取测试，不要求为文档数字而堆测试：

| 层级 | 必须覆盖 |
|---|---|
| 单元 | manifest/兼容元数据解析、能力匹配、Profile 状态转换、错误映射 |
| 集成 | Loader 加载、只读 inventory、Profile patch 启停、配置热更新、Utility 重启、领域 API 权限拒绝、确认写入 |
| 会话回归 | 流式输出、取消、审批、JSONL 恢复、插件缺失与版本变化 |
| 打包 E2E | 默认 Profile 启动、本地 fixture 安装、失败回退、更新、移除、桌面端不中断 |
| 安全 | API Key 不出 Main、未授权写入被拒绝、路径输入和包管理参数不形成命令注入 |

测试 fixture 必须离线可用、行为最小且无真实用户数据。正式发布前再执行项目治理要求的版本、文档、打包和安装验证。

## 13. 推荐提交边界

若工作树已经清理，每个阶段建议独立提交，便于回退：

1. P0：兼容性 spike、fixture、决策记录，不进入用户功能。

4. P2B：inventory、启停、设置 UI 和 Runtime 生命周期。

## 14. 完成定义

当以下事实同时成立，本轮“融合 DSH 插件平台”才算完成：

- 知己默认 Agent 通过 DSH 原生 Profile/Bundle 组合运行。
- 现有复盘领域能力、取消、确认和会话恢复没有回退。
- 高级用户可在桌面设置中查看、启停、配置、安装、更新和移除已核验插件；普通用户默认只看到内置或推荐的复盘扩展。
- 插件变更最多中断 Agent Utility Process，不重启整个桌面应用。
- 知己不向插件提供 API Key 或直接业务仓储，并明确告知可信插件仍拥有其所在 Node 进程的系统权限。
- 至少一个外部示例插件可以按公开文档完成开发和安装。
- 产品主界面仍围绕日志、复盘、项目和行动验证，而不是通用插件控制台。
- 公共市场、任意 UI 和不可信沙箱仍被明确标记为暂缓，而不是以半成品形式混入。
