# 知己 DeepSeek Harness 独立插件执行计划

## 1. 计划目标

把当前阶段已经存在的知己复盘能力转化为一个独立、可安装的 DSH 插件，而不是改造知己桌面端或开发插件平台。

执行成功后的最小结果是：一个已经使用 DSH 的用户，可以通过官方插件命令安装知己 Bundle，在 DSH Web UI 中把一段日志交给知己每日复盘能力，获得有效结果，并能完整移除插件。

本计划不要求桌面端与插件持续源码相同，不建设同步工具、共享 SDK、双向镜像或跨项目强制一致性检查。插件以当前知己能力为开发参考，完成转化后可以独立演进。

## 2. 执行总原则

### 2.1 第一性原理

每个阶段开始前先回答：

1. 这一阶段要解决的 DSH 用户问题是什么？
2. DSH 官方已经提供了哪些能力？
3. 知己插件必须补充的最小部分是什么？
4. 哪个实验能最快证明有用或无用？
5. 如果更简单的 Skill、Prompt 或静态配置已经足够，是否可以不写 Tool 或服务？

“完成更多桌面功能移植”不是自动成立的目标。每增加一种能力，都应说明它如何改善 DSH 内的复盘体验。

### 2.2 高性价比顺序

默认优先级：

```text
DSH 原生 Skill/Prompt
→ 少量 Host Tool
→ 明确的只读文件适配
→ 经确认的写入
→ 自定义 UI（当前不规划）
```

建议优先复用官方公开接口和示例。若执行模型发现更小且符合目标的官方路径，可以采用，但需要在阶段报告说明替代原因和验证结果。

### 2.3 约束强度

以下属于结果边界：

- 不修改或 fork DSH 源码；
- 不改造知己桌面端为插件宿主；
- 插件能够脱离知己桌面端独立安装和运行；
- 不复制 Loader、Profile、HMR、Web UI 和包管理器；
- 不把未知或失败结果写成已实现。

目录、文件拆分、测试组织和内部类名属于实现建议，不作为无必要的硬约束。只要结果边界、官方兼容和验收成立，执行模型可以选择更简单结构。

## 3. AI 执行方式

### 3.1 一次只执行一个阶段

不要在一个任务中连续执行 S1-S4。后续阶段依赖前一阶段的产品和技术证据：

- S1 不成立，则停止插件路线；
- S1 有用但只适合粘贴日志，可以暂不做文件目录；
- 没有真实发布需要，不做 S4；
- DSH Web UI 足够时，不做自定义前端。

### 3.2 开始前上下文

每个阶段至少阅读：

1. `AGENTS.md`。
2. `.claude/shared/ai-operating-principles.md`。
3. `.claude/shared/contracts/first-principles-analysis.md`。
4. `PROJECT_STATUS.md` 与 `CHANGELOG.md` 最近 5 条。
5. `docs/specs/2026-08-21-zhiji-dsh-plugin-architecture.md`。
6. 本执行计划。
7. `docs/reviews/2026-08-21-dsh-plugin-p0-feasibility.md`。
8. 当前阶段需要参考的 `.claude/skills/`、`.claude/agents/` 与 `.claude/shared/` 文件。
9. `D:\AI\deepseek-harness` 中与当前公开接口直接相关的文档、package 和测试。

修改项目文件时同时读取 `docs/development-governance.md`。上游 master 只能作为调查证据；产品依赖必须使用实测的公开 package 入口和明确版本。

### 3.3 工作区与已有改动

开始前检查 `git status --short`。当前仓库可能有用户尚未提交的桌面端和文档改动：

- 不清理、重置、覆盖或吸收来源不明的改动；
- S1 原则上只新增插件独立目录、fixture、测试和必要文档；
- 若与已有改动发生路径冲突，先停在该文件，不通过重写规避；
- 不因为插件实验顺手重构桌面端。

### 3.4 阶段交付

每个阶段应报告：

- 实际解决的问题；
- 使用了哪些 DSH 官方能力；
- 新增了哪些知己插件能力；
- 实际运行的命令和结果；
- 未验证事实和已知限制；
- 是否值得进入下一阶段；
- 如果停止，当前成果怎样保留或移除。

## 5. S1：每日复盘 Bundle MVP

### 5.1 要解决的问题

证明 DSH 用户不安装知己桌面端，也能通过一个官方 Bundle 获得有辨识度的知己每日复盘，而不是只看到一段通用聊天 Prompt。

### 5.2 最小用户流程

```text
安装知己 Bundle
→ 启动或重启 DSH web Profile
→ 用户粘贴一段单日日志并请求每日复盘
→ 知己 Skill/Tool 生成结果
→ 用户在 DSH Web UI 阅读或继续讨论
→ 移除 Bundle
→ Profile 仍可正常启动
```

### 5.3 建议实现范围

第一版建议只包含：

- 一个 DSH Bundle manifest 和 patch；
- 一个每日复盘 Skill，参考当前知己每日分析方法；
- 若 Skill 无法稳定识别材料或输出结构，再增加一个最小 Host Tool；
- 一个或少量脱敏日志 fixture；
- 安装、运行、移除说明；
- 针对当前精确 DSH 版本的验证记录。

可以根据 DSH 官方示例调整 package 结构。不要为了预想中的周报、文件目录或市场先建设通用框架。

### 5.4 当前能力转化原则

执行模型应从当前知己中选择每日复盘必要规则，而不是整仓搬运：

- 输入证据不足时明确降级；
- 优先一个用户不易发现的主要洞察；
- 输出一个可在下一次日志中检查的行动；
- 区分事实、推断和建议；
- 不把自然语言润色当成复盘价值。

插件可以根据 DSH 对话入口调整文案、输出长度和交互方式，不要求与桌面端逐字一致，也不创建同步脚本。

### 5.5 技术验证建议

- 优先在临时 `DSH_HOME` 中使用官方 `dsh plugin` 安装本地预构建 tarball或 directory package。
- 插件初始版本不使用 native dependency、install/prepare script 或任意 Shell。
- Bundle package 使用经过 P0 验证的公开入口，不引用 `D:\AI\deepseek-harness` 的源码路径。
- 验证 Profile 配置、Bundle 重启边界和移除恢复，不追求零重启。
- 优先通过 DSH 现有 Web/headless 测试入口验证；只有需要观察真实浏览器交互时才启动 Web UI。

### 5.6 S1 验收

S1 至少需要证明：

1. Bundle 通过官方命令安装到一个干净 Profile，并在配置中出现。
2. DSH 能加载知己能力，完成至少一个固定日志 fixture 的每日复盘。
3. 输出体现知己的证据、洞察、行动和验证边界，而不是通用摘要。
4. 插件不依赖知己桌面端、仓库绝对路径或修改后的 DSH 源码。
5. 插件移除后不再出现在 Profile，Profile 可以重新启动。
6. 知己桌面端的现有测试和产品行为没有因 S1 改动而回退。

验收可以采用当前阶段最合适的自动化与人工检查组合，不要求为了数字增加无价值测试。实际命令和输出必须记录。

### 5.7 S1 裁决

S1 完成后只允许三种结论：

- **继续**：插件形成了明确每日复盘价值，可以评估 S2。
- **保持 MVP**：每日复盘有用，但暂无扩展证据；发布或内部保留，不继续堆功能。
- **停止**：DSH 适配成本、输出体验或维护成本不值得；保留报告并移除实验接线。

## 6. S2：周期与项目复盘扩展

### 6.1 进入条件

S1 已经真实完成安装、复盘和移除，且至少有一个明确理由说明 DSH 用户还需要周、月或项目复盘。不能仅因为桌面端已有这些功能就自动移植。

### 6.2 建议顺序

优先选择最接近 S1 输入模型的一项，而不是同时实现全部：

1. 周复盘；
2. 月复盘；
3. 项目复盘。

如果 DSH 用户主要粘贴材料，能力可以继续由 Skill 组织；只有需要跨文件范围聚合时才依赖 S3 数据适配。

### 6.3 验收方向

- 范围和材料来源清晰；
- 输入不足时不会伪造周期趋势；
- 输出有别于多篇日报拼接；
- 新能力不破坏 S1；
- 安装包仍可通过官方 Profile 机制移除。

每增加一种复盘，都独立决定是否值得继续下一种。

## 7. S3：日志目录与保存适配

### 7.1 进入条件

真实使用证明“每次粘贴材料”成为主要摩擦，或者周期复盘必须读取多篇 Markdown。没有该证据时保持会话输入即可。

### 7.2 建议实现

先只读：

- 用户显式配置一个日志根目录；
- 支持明确约定的 Markdown 文件；
- 确定性解析日期和范围；
- 只把选中范围的必要材料交给 Agent；
- 路径错误或格式异常清晰失败，不扩大扫描范围。

后续若确需保存报告，再设计明确目标文件、重复运行、覆盖、并发和恢复语义。写入不与只读适配捆绑实现。

### 7.3 与桌面端数据的关系

插件可以读取用户主动指定的知己日志目录，但不把知己桌面端作为运行依赖。第一版不建议桌面端和插件同时写同一正式文件。

两端无需持续同步源码或输出；只需对实际支持的数据格式和写入风险做准确说明。

## 8. S4：独立发布与使用文档

### 8.1 进入条件

至少一个能力已经在仓库外安装包中稳定运行，并且存在给其他 DSH 用户安装的实际意图。

### 8.2 发布内容

- 独立 package version；
- 预构建 npm 包或 GitHub Release tarball；
- 已验证的 DSH 版本；
- 安装、Profile 重启、更新、移除说明；
- 最小示例和数据隐私说明；
- 已知限制；
- `dsh-plugin` GitHub topic。

不建设账号、商店、排行榜、远程审核、自动更新服务或 DSH 桌面发行版。

### 8.3 是否拆仓库

如果插件已经需要独立版本、Issue、贡献者或发布节奏，可以迁移到独立仓库；否则保留为当前仓库中的独立发行 package 也符合架构。

拆仓库时不建设同步工具。插件以拆分时的能力为起点独立维护，需要时人工参考知己后续变化。

## 9. 测试与证据策略

### 9.1 插件自身

建议覆盖：

- Bundle manifest/patch 可被官方 Profile 识别；
- Skill/Tool 能处理代表性材料；
- 输入不足时降级；
- add/remove/restart 闭环；
- package 不依赖开发机绝对路径；
- 已声明兼容版本可运行。

### 9.2 桌面端回归

只有插件实现改动了当前仓库的共享文件或构建配置时，才需要运行对应桌面端测试。若插件目录完全独立，可以选择一组足以证明桌面端未被接线的快速检查，不必每个插件文案改动都执行完整桌面打包。

### 9.3 不要求的同构测试

不建立以下门禁：

- 桌面端和插件源码 hash 相同；
- Prompt 逐字相同；
- 输出 Markdown 逐字相同；
- 两端版本同步发布；
- 自动把 `.claude/` 文件复制到插件；
- 每次桌面端变化都强制更新插件。

插件只需对自己的功能和公开声明负责。

## 10. 风险与处理建议

| 风险 | 高性价比处理 |
|---|---|
| DSH rc 快速变化 | 固定已验证版本；升级前运行兼容测试，不追 latest |
| Skill 表达力不足 | 先确认具体缺口，再增加一个小 Tool |
| DSH Web UI 不够专业 | 先验证核心复盘是否仍有价值；不立即做自定义 UI |
| 插件和桌面能力不同 | 在 README 说明，不做同步系统 |
| 文件目录带来复杂性 | S1 使用粘贴输入，需求出现后再做 S3 |
| 第三方宿主代码信任 | 只发布自己的插件，不为其他插件提供安装平台 |
| 发布维护成本过高 | 保持本地 tarball 或停止，不为简历维持空生态 |
| 两个仓库治理成本 | S1 先作为独立 package，出现独立发布需求再拆仓库 |

## 11. 停止条件

阶段实施中出现以下情况，应优先停止或缩小，而不是继续堆兼容层：

- 必须修改、fork 或复制 DSH 内核；
- 必须使用不稳定 deep import 才能完成基本加载；
- 每日复盘必须依赖知己桌面 Main Process 或大量桌面基础设施；
- 为了一个 Skill 先建设共享 SDK、同步工具或复杂代码生成；
- DSH Web UI 中的复盘体验无法体现知己方法的价值；
- 需要自建安装器、市场或桌面发行版；
- 实际使用证据不足，后续阶段只剩“功能列表更完整”的收益；
- 维护成本明显高于独立插件带来的用户和项目叙事价值。

证明路线不值得继续也是有效结果，不能用扩大范围掩盖失败。

## 12. 提交与文档边界

每个阶段建议形成独立提交，便于保留或回退：

1. S0：架构、计划和旧路线状态。
2. S1：每日复盘 Bundle、fixture、测试和开发说明。
3. S2：每一种新增复盘能力独立提交。
4. S3：只读适配与可选写入分开提交。
5. S4：发布元数据和用户文档。

执行时遵守项目现有版本、CHANGELOG、PROJECT_STATUS 和提交规则。不要把当前工作区来源不明的改动一起提交。

## 13. 下一步

S0 完成后停止。只有用户明确要求实施 S1，执行模型才开始创建插件 package 和每日复盘 MVP。

S1 的第一项工作不是铺设完整目录，而是用 DSH 官方公开教程确认最小 Bundle 形状，并选择当前知己每日复盘中真正需要转化的规则。完成 S1 后先展示实际 DSH 结果，再决定 S2。
