# 第一性原理提醒

> 这不是 AI 的操作手册，也不是项目规范。它是给“建的人”和“用的人”看的提醒：别把工具做得越来越复杂，却忘了它为什么存在。

> 当前版本、项目进度、已知问题与待办事项以 `PROJECT_STATUS.md` 为准；这里尽量只保留长期稳定的原则提醒。

## 一句话

知己不是为了生成更多报告，而是为了发现你自己看不到的模式，并促成可验证的行为改变。

## 最小成功定义

```text
至少有一条洞察，用户自己不会发现，
并且它导致了至少一个可验证的行为改变。
```

如果这个从未发生过，版本号是 0.18 还是 18.0 没有区别。

## 为什么需要它

人有三个天然盲区：

| 盲区 | 表现 |
|------|------|
| 观察者悖论 | 你能感到“最近状态不好”，但很难在当下看见跨时间模式。 |
| 遗忘曲线 | 你今天写下的深刻洞察，半个月后可能已经忘了。 |
| 自我叙事偏差 | 你以为自己应该稳定执行，但真实高效模式可能是外部触发后的集中爆发。 |

AI 的价值不在于替你下结论，而在于做一个假说生成器：它能跨时间看模式，也能不顾情面地指出重复，但最终判断必须回到你的真实体验和行动结果。

## 原子价值公式

```text
价值 = (洞察质量 × 可行动性 × 闭环速度) / 使用摩擦
```

- **洞察质量**：看到你自己反思得不到的发现。
- **可行动性**：能变成明天的一个具体动作。
- **闭环速度**：从写日志到读反馈，再到第二天验证的速度。
- **使用摩擦**：从“想分析”到“看到结果”需要做多少额外决定。

## 开发者纪律

打开编辑器想改项目时，先问：

1. 这个改动会更容易产生“用户自己发现不了的洞察”吗？
2. 这个改动会降低使用摩擦，还是只是在增加结构完整性？
3. 我最近有没有以用户身份真实跑过一次日反馈？

优先级永远是：

```text
用优先于建
日反馈优先于周/月报
闭环速度优先于分析全面性
被验证的改变优先于好看的故事
```

如果连续几天都在开发，却没有粘贴日志、读反馈、验证行动，你很可能已经在打磨工具，而不是使用工具。

## 用户纪律

最小闭环只有四步：

```text
写日志 → 粘贴 → 读反馈 → 第二天记录验证结果
```

读完反馈后，至少留下一行：

```text
新认知：[以前没看到的事] | 行动：[做/没做] | 验证：[对/错/待验证]
```

如果连续几次“行动=没做”，不要继续责怪自己。降低行动门槛，或者质疑这条洞察是不是找错了根因。

## 共同原则

| 原则 | 反例 |
|------|------|
| 闭环速度 > 分析全面性 | 等 9 个视角全跑完才看反馈。 |
| 被验证的洞察 > 好看的故事 | 报告写得很好，但一周后什么都没变。 |
| 小量持续 > 大量冲刺 | 一天写 3000 字，然后一周不写。 |
| 系统服务用户 | 为了喂饱 AI 视角而刻意写某种日志。 |
| 删比加更需要勇气 | 加新功能很像进步，删掉无用功能才是真的降低摩擦。 |

## 反模式

### 开发者反模式

| 反模式 | 自救 |
|--------|------|
| 为完整性加功能 | 先证明已有链路能产生行为改变。 |
| 用架构复杂度自我感动 | 问：删掉这一层，用户会感知到价值损失吗？ |
| 没有数据时优化管道 | 先跑真实日志，等数据量成为瓶颈再优化。 |
| 把未来可能需要当成现在就要做 | 让需求从使用中长出来。 |

### 用户反模式

| 反模式 | 自救 |
|--------|------|
| 堆积日志不分析 | 下次打开项目，先跑一次日反馈。 |
| 读完分析不追踪 | 立刻写“新认知 / 行动 / 验证”。 |
| 全信 AI | 找反例，观察一周再判断。 |
| 状态不好就不写日志 | 写 3 句话：发生了什么、感受是什么、明天想做什么。 |
| 把系统当日记本 | 至少写一个“为什么”。 |

## 两个身份的对话

**开发者说**：我想再加一个功能。

**用户说**：先告诉我，最近一次日反馈里建议的行动，我做了吗？

**开发者说**：还没验证。

**用户说**：那先别加。让我把今天的日志贴进去。

---

**用户说**：这份分析看起来很有道理。

**开发者说**：它有没有说出你自己没看到的东西？

**用户说**：有。

**开发者说**：那明天验证它。验证前，它只是一个漂亮假说。
