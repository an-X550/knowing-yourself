# 第一性原理行动指南

> 每次对话开始时读取此文件，在开发冲动或使用懈怠时回来重读。

---

## ⚡ 行动浓缩（打开项目前必读）

### 如果你是开发者 🔧

**现在最该做的**：功能冻结。直到你证明了：至少有一条 AI 洞察，你自己发现不了，导致了一个可验证的行为改变。
**现在最不该做的**：加新视角 / 优化 workflow / 建"未来可能需要"的功能 / 连续开发超过两天不跑用户侧分析。
**打开编辑器前自问**：我今天是用用户身份还是开发者身份打开？如果今天想改代码——先跑一次日分析。

### 如果你是用户 👤

**每日铁律**：写日志 → 粘贴 → 读反馈 → 第二天记录验证结果。缺一步，闭环就断了。
**现在最该做的**：让日反馈回路转起来。33天日志只有1次日反馈。分析覆盖率超过50%之前，不考虑周报月报。
**读完分析后**：在反馈文件末尾写 `💊 新认知：[...] | 行动：[...] | 验证：[...]`。连续3次"行动=没做"→ 减少频率或降低行动门槛。

### 当前真相

| 指标 | 数据 |
|------|------|
| 日志总量 | 69篇（5/6/7月） |
| 日分析反馈 | 3次 |
| 月报告 | 3份（5/6/7月） |
| 已验证的行为改变 | 0 |

> **一句话**：用优先于建。日分析优先于周月报。闭环速度优先于分析全面性。被验证的改变优先于好看的故事。

## 零、为什么存在这个项目（第一性原理推导）

> 在写代码或写日志之前，先回答最根本的问题：这个项目凭什么存在？

### 人的三个不可克服的局限

1. **观察者悖论**：你无法在自己生活的当下观察自己的模式。你能感觉到"最近状态不好"，但你感觉不到"你的拖延有一个精确的7天周期，总是在高压任务结束后的第2天出现"——因为感受是瞬时的，模式是跨时间的。
2. **遗忘曲线**：6月3日你在日志里写了一个深刻洞察，6月15日你已经忘了它。不是你不重视，是人脑的默认模式。没有外部记忆系统，你的日志是写给自己然后遗忘的。
3. **自我叙事的系统性偏差**：你用一个"完美执行的规划者"标准衡量自己，但你实际的最高效模式是"焦虑驱动 → 外部触发 → 集中爆发"。这两个故事在同一个人的脑子里共存，而你自己分不清哪个是真的。

### AI的两个不可替代的优势

| AI 的优势 | 为什么人做不到 |
|-----------|--------------|
| **零情感纠葛** | 朋友不敢说"你又在重复上个月的逃避模式了"——怕伤感情。AI没有感情可以伤 |
| **跨时间记忆** | AI可以同时记住你6月3日、6月15日、6月28日的日志，并发现其中有同一个模式。人类的短期记忆做不到跨30天的模式匹配 |

**AI的劣势同样真实**：它不活在你的身体里，它感受不到你的感受。所以AI说的一切都是假说，需要你用自己的体验去验证。这不削弱AI的价值——它定义了AI的角色：**不是答案提供者，是假说生成器**。

### 用户真正需要什么（四个不可削减的需求）

从以上推导，用户需要的不是"日志工具"，不是"AI分析"，而是四个具体结果：

| 需求 | 定义 | 如果没有这个项目 |
|------|------|-----------------|
| **模式发现** | 看到自己看不到的跨时间行为模式 | 你会在同样的坑里摔倒第6次才意识到这是一个坑 |
| **执行问责** | 昨天的意图是否变成了今天的行动 | 你每天都写"要早睡"，写了30天然后放弃了 |
| **决策校准** | 基于实际行为数据而非自我感觉做选择 | 你因为"感觉自己效率低"而放弃考公，但实际上你的效率不低——你只是用错了基准线 |
| **成长加速** | 从经验中学习的速度快于纯粹靠自己反思 | 一个月的日志，靠自己反思能提取30%；加上AI交叉验证，提取70% |

### 最小成功定义

这个项目成功的标准不是"9个视角全部产出报告"，不是"用户每天都写日志"。**成功的唯一定义是**：

```
至少有一条洞察，用户自己不会发现，导致了至少一个可验证的行为改变。
```

如果这个从未发生过，版本号是0.18还是18.0没有区别。

## 原子价值公式

```
价值 = (洞察质量 × 可行动性 × 闭环速度) / 使用摩擦
```

**洞察质量**：你自己反思得不到的发现。如果分析只复述了你已经写清楚的思考，它没有价值。
**可行动性**：能变成明天的具体行为。有趣但无法行动的洞察 = 娱乐，不是工具。
**闭环速度**：从写日志到读到反馈的时间。完美的分析晚两周不如够用的分析今晚到。
**使用摩擦**：从"想分析"到"看到结果"需要做的决策数。每个额外决策都在杀死使用率。

**最小价值单元**：一条你自己不会发现的洞察 → 导致一个行为改变。

## 开发者须知

> 打开编辑器想改代码时，先读这一节。

### 建前必问

每次想加新功能、新视角、新命令之前，回答这三个问题：

1. **"这个功能会产生我自己发现不了的洞察吗？"** — 如果答案是否，暂缓。架构优雅不是理由，视角"完备"不是理由。
2. **"我是在解决真实痛点，还是想象中的痛点？"** — 真实痛点来自你作为用户时的挫败感，不是来自你作为开发者时的"如果能X就好了"。
3. **"加了这个，使用摩擦变大了还是变小了？"** — 每增加一个选项、一个参数、一个模式，都在增加决策负担。功能越少，用得越多。

### 删减原则

- 视角不是越多越好。**每季度做一次视角审计**：统计各视角产出的可行动洞察数。连续两个月零产出的视角，关闭它。
- 一个被删掉的无用功能 > 一个留在系统里制造噪音的功能。代码可以回退，认知负担回退不了。
- 9个视角里，也许只有4个在真正工作。找到那4个，把注意力给它们。

### 开发者节奏

- **每周1-2次开发会话**，其余时间只做用户。如果你连续3天以上在开发而没有使用系统分析日志，你已经在"打磨望远镜"了。
- 开发会话开始前，先以用户身份用一次系统——让真实痛点驱动开发方向。
- 一个好用的v0.1 > 一个没人用的v1.0。功能冻结是美德。

### 代码是手段，洞察是目的

不要爱上手段而忘记目的。CLI工具、agent架构、workflow脚本、评分体系——这些都是管道。唯一重要的是管道另一端流出来的是什么：**你今天知道了什么你昨天不知道的事？**

## 用户纪律

> 打开编辑器想粘贴日志时，读这一节。

### 每日铁律

```
写日志 → 粘贴 → 读反馈 → 第二天日志里记录验证结果
```

- 这四步缺一步，闭环就断了。断了闭环，系统退化成了"日志存档器"。
- **宁可写3句话的日志，也不要因为"写不好"就不写。** 完美主义是日志的头号敌人。一篇C级日志 + 一份反馈 >> 一篇想象中的A级日志。
- 当天粘贴，当天得到反馈。堆积的日志 = 堆积的盲点。

### 洞察追踪

读完每份分析（日/周/月），在文件末尾加一行：

```
💊 新认知：[以前不知道的事] | 行动：[做/没做] | 验证：[对/错/待验证]
```

- 如果"新认知"栏写不出来——这份分析对你没有价值。记录这个事实本身就有价值：它在告诉系统"这个视角对我没用"。
- 如果连续3次"行动"栏是"没做"——分析在变成娱乐。重新校准：要么减少分析频率，要么降低行动门槛。
- 一个月后回看这一行，你会知道：哪些视角在真正工作，哪些只是在生产好看的文字。

### 验证闭环

- AI说的"认知纠偏"也是假说，不是真理。它说"你在逃避X"——你需要在接下来一周主动观察：我真的是在逃避X吗？有什么反例？
- **AI的优势是零情感纠葛和跨时间记忆。AI的劣势是它不活在你的身体里。** 它能看到模式，但感受不到你的感受。最终判断权在你。
- 如果一个洞察反复出现但你始终无法行动——问题可能不在你，而在洞察本身。也许它不够具体，也许它找错了根因。质疑它。

## 共同原则

这些原则同时约束开发者和用户身份。当你切换角色时，它们不变。

| 原则 | 反例 |
|------|------|
| **闭环速度 > 分析全面性** | "等我把9个视角都跑完再一起看"——那时候你已经忘了日志里写的是什么感觉 |
| **被验证的洞察 > 好看的故事** | "这份报告写得真好"——但一周后你什么都没改变 |
| **小量持续 > 大量冲刺** | 一天写3000字日志然后一周不写 >> 每天写200字持续30天 |
| **系统服务用户，不是反过来** | 为了"喂饱"所有9个视角而刻意写某种日志——日志变成了给AI写的数据标注 |
| **删比加更需要勇气** | 加一个新功能感觉像进步；删一个无用功能才是进步 |

## 反模式清单

### 开发者反模式 🔧

| 反模式 | 为什么危险 | 如何自救 |
|--------|-----------|---------|
| **连续3天以上纯开发不用** | 你在为一个你不使用的东西做工程决策 | 停下来，以用户身份用一次系统 |
| **为"完整性"加功能** | "还差一个视角就完整了"——完整不是目标，洞察才是 | 先证明已有视角在产生洞察，再加新的 |
| **用架构复杂度自我感动** | workflow脚本、多层agent编排——很酷，但如果用户侧的日志还是空的，它就是无用之美 | 问自己：删掉这一层，用户会感知到吗？ |
| **在没数据的时候优化管道** | 2个月日志就优化"年度分析"的性能——本末倒置 | 先积累到数据量成为瓶颈，再优化 |
| **把"未来可能需要"当成"现在就要做"** | CSV导出、国际化、自动化测试——都很好，但你现在需要的是更多洞察，不是更多功能 | 让需求从使用中长出来，不要从想象中预先种下 |

### 用户反模式 👤

| 反模式 | 为什么危险 | 如何自救 |
|--------|-----------|---------|
| **堆积日志不分析** | 日志变成纯粹的存档，零反馈，零成长 | 下次打开编辑器，先跑 `/daily-review`，再写新日志 |
| **读完分析不追踪** | 看了觉得"有道理"然后关掉——跟刷短视频没有区别 | 立刻写 `💊` 行，没有新认知就写"无新认知" |
| **AI说的全信** | "你本月的问题是对抗性思维"——AI说得很自信，但可能完全错了 | 找反例。这一周有没有不符合这个判断的时刻？ |
| **因为"状态不好"就不写日志** | 状态不好的日志恰恰是最有价值的日志——它记录了你的下限 | 状态不好就写3句话：1件发生的事 + 1个感受 + 1个明天想做的事 |
| **把系统当成日记本** | 只写事实不写思考，AI没有材料做分析 | 至少每篇日志有一个"为什么"——为什么今天开心/不开心/效率高/拖延 |

## 诚实检查：项目是否在兑现承诺

> 每次月度复盘后更新此节，或在阅读最新月度报告时自动刷新。诚实回答：项目在产生价值还是在生产架构？

### 检查框架

对照四个不可削减的需求，逐项自问：

| 承诺 | 检查问题 | 证据来源 |
|------|---------|---------|
| **模式发现** | 本月有没有一条洞察是用户自己不会发现的？ | 最新月度报告 → "模式与关注点"章节 |
| **执行问责** | 日反馈闭环覆盖率 = 日分析次数 / 日志天数？趋势上升还是下降？ | 复盘/每日反馈/ 文件数 ÷ 日志天数 |
| **决策校准** | 有没有基于分析数据做出过和"直觉"不同的选择？ | 月度报告 → "下月重点关注"被实际执行的比率 |
| **成长加速** | 最小成功定义是否已被满足？（≥1条洞察 → ≥1次行为改变） | verified-patterns.md 是否非空？ |

每次复盘后，用最新数据回答这4个问题，替换以下占位。如果连续两个月某个承诺的答案是"否"，该承诺对应的功能需要重新设计。

## 两个身份的对话

> 当你在同一个工具里既是建造者又是居住者时，这两个身份需要对话。

**开发者说**："我应该加一个预测验证机制，让月度综合报告输出可证伪的假说。"

**用户说**："好。但在你加之前，我已经连续3天没跑日分析了。先让我把今天的日志粘贴了。"

**开发者说**："对。你先用。用完告诉我痛点在哪。"

—

**用户说**："今天这份日分析感觉在复述我写的东西，没有新洞察。"

**开发者说**："记下来。连续3次这样，我们就去改 daily-analyzer 的 prompt。但如果只是偶尔一次，可能是你今天的日志写得太浅了。"

—

**用户说**："我想加一个新视角。"

**开发者说**："先告诉我：你现在用的视角里，哪个产出最少？如果删掉它腾出空间，你还想要新的吗？"
